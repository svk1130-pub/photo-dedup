# Архитектура Photo Dedup

> Это описание верхнего уровня: состав приложения, таблицы БД, маунты, принципы.
> Подробная логика движка — [LOGIC.md](LOGIC.md), расширенная версия с фрагментами
> кода — [LOGIC_EXT.md](LOGIC_EXT.md), дизайн Streamlit-фронта — [UI_DESIGN.md](UI_DESIGN.md).

## 1. Состав приложения

Приложение решает одну задачу: в большом фотоархиве (до 3 ТБ, сотни тысяч файлов,
вложенные подпапки) найти дубликаты — в том числе **изменённые, повёрнутые,
зеркальные** — и перенести их в `trash`, не удаляя. Состоит из четырёх независимых
процессов (в docker — контейнеров), которые общаются **только через PostgreSQL**:

```
┌─────────────────────┐         ┌───────────────────────┐         ┌──────────────────────┐
│  engine (CLI)       │         │  PostgreSQL 16 (db)   │         │  web (Streamlit)     │
│  scan/analyze/move/ │──W──▶   │  files, hashes,       │  ◀──R── │  :8501 (порт хоста   │
│  run/undo/clean-db/ │──W──▶   │  groups, runs,        │  ──W─▶  │  9501), тонкий       │
│  status/stop        │         │  status, events,      │         │  клиент, пул ≤ 5     │
└─────────────────────┘         │  jobs (очередь, 1.5)  │         └──────────────────────┘              named volume pgdata
┌─────────────────────┐         └───────────┬───────────┘
│  runner (1.5)       │◀───LISTEN jobs / SKIP LOCKED                  restart: unless-stopped
│  вечный цикл: взял задание из очереди — выполнил код движка in-process     http://localhost:9501
└─────────────────────┘
```

* **engine** — CLI-процесс (`python -m engine.cli <команда>`). Вся тяжёлая работа:
  обход ФС, хэширование (8 phash-вариантов D4), поиск групп, физический перенос
  файлов, отмена переносов. Не автозапускается и не рестартует — запускается
  человеком командой `docker compose run --rm engine <команда>`.
* **runner** (1.5.0 Ф1 + 1.6.0 Ф2) — исполнитель очереди `jobs`: тот же образ,
  маунты и env, что у engine; вечный цикл (`restart: unless-stopped`) — атомарно
  забирает задание (`FOR UPDATE SKIP LOCKED` + single-flight guard по
  `status.stage`) и выполняет команду движка **in-process** — тот же код, что у
  CLI, без subprocess и docker-сокета. Пробуждение — LISTEN/NOTIFY (фоллбэк —
  опрос); живость — heartbeat в `jobs`; зависшие задания помечаются stale на
  рестарте runner'а (crash-recovery) и периодически из UI; после каждого
  `finish` история ужимается до последних `RUNNER_RETAIN_JOBS` записей
  (retention, 1.6.0). Resume команд продолжит прерванную работу.
* **db** — `postgres:16-alpine`, единственная точка обмена данными; healthcheck
  `pg_isready`, данные в named volume `pgdata`.
* **web** — Streamlit-фронтенд. Тонкий клиент: читает БД (пагинация, агрегаты),
  пишет флаги/команды, ставит задания в очередь `jobs` (кнопки запуска на
  Мониторе — просто INSERT) и выполняет точечные файловые операции
  (`engine/webops.py`). Процессы не запускает; stale-детекция очереди
  (reap по протухшему heartbeat) выполняется и здесь (1.6.0).

**Ключевая особенность решения:** движок можно запускать **как угодно** —
из командной строки хоста (`python -m engine.cli run` без docker) или командой
`docker compose run --rm engine run` — и при этом:

* UI не является обязательным: движок корректно отрабатывает при полностью
  закрытом браузере (флаги остановки и настройки лежат в БД/файле, а не в памяти UI);
* UI не является «пультом с subprocess»: он никогда не запускает процессы.
  Кнопки запуска на Мониторе лишь вставляют строки в очередь `jobs`, задание
  выполняет отдельный сервис `runner` (тот же образ/код, что и CLI); все прочие
  взаимодействия — флаги в БД и точечные файловые операции. Почему через очередь
  и без docker-сокета — разбор в [WHY_NO_BUTTONS.md](WHY_NO_BUTTONS.md) §5;
* управление настройками общее: `settings.toml` — один host-файл, примонтированный
  в оба контейнера (engine — `:ro`, web — `rw`), поэтому правки из UI мгновенно
  видны CLI и наоборот.

## 2. Таблицы БД (DDL идемпотентный — `engine/db.py`, выполняется при старте движка)

| Таблица | Назначение |
|---|---|
| `files` | Индекс архива: `path UNIQUE`, `size`, `mtime`, `width`/`height`, `indexed_at`, `status` (`ok` \| `corrupt` \| `moved`), `error`, **`exif JSONB`** (свойства для окна «ℹ️ Свойства»; заполняются на scan либо лениво из UI) |
| `hashes` | 8 phash-вариантов D4 на файл: `(file_id, variant) PK`, `phash BYTEA`, `hash_part TEXT` (ключ бакета), индекс по `hash_part` |
| `analysis_runs` | История прогонов analyze: `created_at`, `threshold`, `params JSONB` |
| `groups` | Группы дубликатов: `run_id`, `member_count`, `total_size`, `kept_path`, `confirmed` (для manual-переноса), `info JSONB` (min_distance, group_dir, точные копии и пр.) |
| `group_members` | Состав групп: `(group_id, file_id) PK`, `role` (`kept`\|`dup`), `moved_to`, `moved_at` |
| `status` | Синглтон (`id=1`): этап, прогресс, скорость, текущий файл, `engine_pid`, флаг `stop_requested`, `params JSONB` — по нему UI и CLI видят, что делает движок |
| `events` | Структурированный журнал: `ts`, `level`, `message`. Пишут движок, ручные операции и обслуживание; UI показывает хвост 200 записей |
| `jobs` | Очередь заданий runner'а (1.5.0): `command` (`run/scan/analyze/move/undo`), `params JSONB`, `state` (`queued → running → done/failed/stopped/stale`), `requested_at` / `taken_at` / `finished_at` / `heartbeat_at`, `runner_id`, `exit_code`, `error`, `result JSONB`. Частичный уникальный индекс `uniq_jobs_queued_command`: одно queued-задание на команду |

Журнал — в БД, а не в файле: у контейнеров нет разделяемой ФС, а БД даёт
упорядоченность, уровни и лёгкий доступ из UI. Старые записи подчищаются
(хранятся последние ~1000).

Миграции схемы — идемпотентные и обратно совместимые, выполняются при каждом
старте движка и runner'а: снятие/установка CHECK на `files.status` (1.3.0),
`ALTER TABLE files ADD COLUMN IF NOT EXISTS exif JSONB` (1.4.0),
`CREATE TABLE IF NOT EXISTS jobs` + индексы очереди (1.5.0). Отдельного
шага «миграция» при обновлении не требуется.

## 3. Маунты и путь-маппинг (хост ↔ контейнер)

| Маунт | engine | web | Зачем |
|---|---|---|---|
| `${PHOTOS_ROOT}/src → /data/src` | rw | rw | Архив; движку — перенос из него, UI — точечные операции ⭐/↩️ |
| `${PHOTOS_ROOT}/trash → /data/trash` | rw | rw | Приёмник дубликатов; UI — 📋/🗑️/undo |
| `./settings.toml` | `/app/settings.toml` **ro** | `/data/settings.toml` **rw** | Единый файл настроек |
| `./docs → /app/docs` | — | **ro** | Вкладка «🧠 Логика» читает `LOGIC.md` без пересборки образа |
| volume `pgdata` | — | — | Данные PostgreSQL |
| volume `thumbs` (`/data/cache`) | — | rw | Дисковый кэш миниатюр |

**Где лежат фото на хосте — задаёт ОДНА переменная `.env`: `PHOTOS_ROOT`**
(образец — `.env.example`; по умолчанию `./` — папки рядом с compose-файлом).
Контейнерные пути при этом фиксированы (`/data/src`, `/data/trash`), поэтому:

* секция `[paths]` в `settings.toml` не зависит от того, где физически архив —
  перенос архива на другой диск/машину не требует правки настроек;
* в UI сайдбар показывает соответствие: `/data/src` → «на хосте: `$PHOTOS_ROOT/src`»
  (`engine/settings.py: container_to_host`);
* смена хост-папки — правка `.env` + `docker compose up -d` (пересоздание
  контейнеров с новыми маунтами). Правка `[paths]` из UI маунты не меняет
  принципиально — поэтому она в UI не редактируется, а показывается с подсказкой.

Приложение работает под non-root пользователем `appuser` (uid 1000); bind-маунты
сохраняют права хоста — папки `src`/`trash` создаются своим пользователем
(или `chown 1000:1000`), см. README §7.

## 4. Команды движка (CLI)

| Команда | Что делает |
|---|---|
| `scan` | Индексация файлов + 8 phash-вариантов; Resume по `(path, size, mtime)` |
| `analyze` | Поиск групп дубликатов по бакетам hash_part + union-find; создаёт `analysis_runs` |
| `move` | Перенос дубликатов в trash (auto/manual, dry-run, sha256-верификация, crash-recovery) |
| `run` | scan → analyze → move с перечитыванием настроек на границах этапов |
| `undo` | Отменить все переносы: вернуть файлы из trash в src; при успехе — TRUNCATE результатов и журнала. `--dry-run` — только план |
| `clean-db` | Очистить результаты прогонов и журнал (файлы на диске не трогаются) |
| `status` / `stop` | Лёгкие команды: показать статус / выставить флаг мягкой остановки |

Те же операции обслуживания доступны и из UI (Монитор → «🧨 Опасная зона»):
«💥 Очистить БД» = `clean-db`, «↩️ Отменить всё» = `undo`. В UI они запрещены,
пока движок работает (guard по `status.updated_at`), — как и точечные операции
с файлами в галерее.

**Запуск через очередь (1.5.0 Ф1 + 1.6.0 Ф2).** Кнопки запуска на Мониторе
(▶️ Полный прогон / 🔍 Скан / 🧠 Анализ / 📦 Перенос / ↩️ Undo) ставят задание
в таблицу `jobs` (INSERT + `pg_notify`); его забирает и выполняет сервис
`runner` — тот же код движка, что и у CLI. В очередь ставятся только долгие
команды (`run/scan/analyze/move/undo`; undo — только через подтверждение в
UI); `clean-db`, `status`, `stop` остаются прямыми операциями (быстрые/
интерактивные, у clean-db — своё подтверждение). Дубликат queued-задания той
же команды отсекается на уровне БД. Прогресс и итоги заданий — Монитор:
блок «Очередь runner» (текущее, история, exit-коды, «прогон оборвался» при
stale); история ограничена retention'ом (`RUNNER_RETAIN_JOBS=200`), «💥
Очистить БД» вычищает её целиком.

## 5. Тонкий клиент и границы ответственности

* **Движок** не знает о UI: пишет статус/события/результаты в БД и читает флаги.
* **UI** не запускает движок как subprocess; тяжёлые вкладки — `st.fragment`
  с автообновлением; все выборки — с LIMIT/агрегатами; миниатюры — ленивые,
  из дискового кэша. Единственные файловые операции UI — точечные
  (`engine/webops.py`: одна-две операции `shutil.move`/`os.unlink` по путям
  из БД, без обходов дерева), и они блокируются на время работы движка.
* **БД** — граница согласованности: транзакции коммитятся ПОСЛЕ файловых
  операций (в move и webops), поэтому crash-recovery восстанавливает картину
  по фактическому состоянию диска.

Подробнее о приёмах производительности UI (фрагменты, пул, кэш миниатюр,
метрика «UI rerun < 300 мс») — [UI_DESIGN.md](UI_DESIGN.md).
