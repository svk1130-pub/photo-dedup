# Логика работы движка (подробно)

> Этот файл показывается во вкладке «🧠 Логика» UI. Расширенная версия
> с фрагментами кода — [LOGIC_EXT.md](LOGIC_EXT.md); архитектура —
> [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. Общая схема

Движок работает поэтапно. Каждый этап — отдельная команда CLI, а `run`
выполняет все три с перечитыванием `settings.toml` на границах этапов:

```
scan  ──▶  analyze  ──▶  move
(индексация)  (группы)    (перенос в trash)
```

Инварианты, на которых держится вся логика:

* **БД — единственный источник истины о прогрессе.** Файловые операции
  делаются ДО коммита транзакции, которая фиксирует их результат. Если движок
  упал между «файлы перенесены» и «БД обновлена», повторный запуск
  восстанавливает картину (crash-recovery, §4.5).
* **Ничего не удаляется необратимо** (кроме явной команды пользователя):
  дубликаты переносятся в `trash` с отчётом `info.txt`, есть `undo`.
* **Dry Run главнее переноса**: `move --dry-run` физически ничего не делает
  и не меняет БД — только фиксирует план в журнале (`events`).

## 2. Этап scan — индексация (`engine/scan.py`)

1. **Обход дерева.** `os.walk` по `paths.src` с пропусками: папка `trash`,
   скрытые каталоги/файлы, симлинки (защита от циклов). Фильтр по
   `scan.extensions` (регистр не важен), `scan.recursive` управляет глубиной.
2. **Знаменатель прогресс-бара** (сколько всего файлов-кандидатов) считается
   в фоновом потоке-демоне параллельно с хэшированием — двойной обход дерева
   на холодном кэше (минуты на больших архивах) устранён; как только счёт
   готов, он подхватывается в статус.
3. **Хэширование.** `ThreadPoolExecutor(scan.threads)`: воркеры ТОЛЬКО вычисляют
   хэши; все записи в БД делает главный поток пачками по `scan.batch_size`
   в одной транзакции (`executemany`) — нет конкурентной записи, статус
   обновляется раз в батч.
4. **Resume.** Файл пропускается, если в БД есть строка с тем же
   `(path, size, mtime)` и хэши на месте. Изменившийся файл переиндексируется
   (его старые хэши сначала удаляются). `--force` — переиндексировать всё.
   «Битые» файлы (`status='corrupt'`) не ретраятся каждый запуск, но изменение
   mtime переводит их обратно в кандидаты.
5. **Обработка одного файла** (`engine/hashing.py: compute_entry`):
   * `img.draft("RGB", (512,512))` для JPEG/MPO — черновое декодирование до
     ~512 px до любого обращения к пикселям (многократное ускорение);
   * EXIF-поворот применяется явно (`ImageOps.exif_transpose`) — Pillow сам
     его не применяет; ширина/высота в БД хранятся «как видит человек»;
   * **8 phash-вариантов D4** (§3);
   * при `scan.read_exif=true` (дефолт) — извлечение EXIF-свойств
     (камера, выдержка, диафрагма, ISO, вспышка, замер, фокусное, дата
     съёмки) в `files.exif JSONB` для окна «ℹ️ Свойства» галереи. Читаются
     ТОЛЬКО заголовки APP1 (без декодирования пикселей), поэтому стоимость
     ничтожна на фоне phash; любая ошибка EXIF не прерывает индексацию.
     Если отключить — свойства будут читаться лениво при первом открытии
     окна «Свойства» и кэшироваться в БД.

## 3. Алгоритм поиска дубликатов

### 3.1 Перцептивный хэш и инвариантность к D4 (`engine/hashing.py`)

`imagehash.phash` (hash_size=8 → 64 бита) устойчив к перекодированию, ресайзу
и лёгкой цветокоррекции, но не к поворотам/отражениям. Поэтому для каждого
файла считаются **8 хэшей — по всем элементам группы D4**: identity, 3 поворота
(90/180/270), 2 отражения (лево-право, верх-низ) и 2 диагональных
(TRANSPOSE, TRANSVERSE — композиция отражения и поворота). Никакой
«min-канонизации»: композиция отражения и поворота не входит в набор из 5
трансформаций Pillow, и зеркальные копии терялись бы. Байт-в-байт копии дают
идентичные наборы хэшей всегда.

### 3.2 Бакеты и расстояние Хэмминга (`engine/analyze.py`)

Полный перебор O(n²) по всему архиву невозможен, поэтому:

1. Все хэши делятся на **бакеты по префиксу `hash_part`** (по умолчанию 4 hex
   символа = 16 бит ≈ 1/65536): кандидаты обязаны совпадать первыми 16 битами.
   Это документированный trade-off: пара, различающаяся в первых 16 битах,
   не будет найдена. Важно: у байт-в-байт копий совпадает ВЕСЬ хэш, поэтому
   они находятся при любом пороге.
2. Внутри бакета — попарное расстояние Хэмминга по полному 64-битному хэшу:
   XOR + popcount, векторизовано numpy (`np.bitwise_count`). Пары считаются
   **2D-блоками 1024×1024** — пик памяти ограничен десятками МБ независимо
   от размера бакета (десятки тысяч «похожих» кадров не приводят к OOM).
3. Кандидат — ЛЮБАЯ пара вариантов (файл A, вариант i) ↔ (файл B, вариант j)
   с дистанцией ≤ `analyze.threshold`.
4. **Группы — транзитивное замыкание** через union-find внутри бакета:
   A~B, B~C ⇒ одна группа, даже если A!~C. В `groups.info` сохраняется
   минимальная дистанция в группе.
5. Хэши разной длины (смена `hash_size` без `--force`) несравнимы — бакет
   делится на подгруппы равной длины и обрабатывается независимо.

**`analyze.threshold` — главный регулятор точности:** 0 — только «те же самые»
(и повёрнутые/зеркальные) кадры; 1–4 консервативно; выше — агрессивнее
(серии съёмки могут склеиваться). Изменение порога не требует переиндексации —
только перезапуска `analyze`.

## 4. Этап move — перенос дубликатов (`engine/move.py`)

### 4.1 Режимы

* `move.mode = auto` — переносятся ВСЕ группы последнего run;
* `move.mode = manual` — только группы с `confirmed=true` (кнопки в UI
  «✅ Подтвердить»/«✅ Подтвердить все») или конкретная группа через
  `move --group-id N` (работает даже без подтверждения);
* `move.dry_run = true` (или флаг `--dry-run`) — только план в журнале,
  физически ничего не переносится и БД не меняется (включая recovery-ветки).

### 4.2 Что считать «оригиналом» (`move.keep_by`)

Роль «оригинала» (kept) определяется на момент переноса, не заранее:

* **`capture` (дефолт)** — по времени снимка. Иерархия источников на файл
  (`engine/originals.py`):
  1. **Takeout-sidecar** `<файл>.json` рядом: `photoTakenTime` → `creationTime`
     (парсится только `timestamp`; локализованное `formatted` игнорируется
     принципиально; мусор и «будущее» отбрасываются; мс-epoch → секунды);
  2. **Файловая система**: `min(birthtime, mtime)`. Копии наследуют mtime
     источника, но получают НОВЫЙ birthtime — минимум двух времён ≈ момент
     появления контента. На Windows роль birthtime играет `st_ctime`;
     если ФС не хранит birthtime (часть Linux) — остаётся mtime;
  3. mtime из БД (файл недоступен — редкий edge на этапе move).
* **`size`** — максимальный размер файла; **`pixels`** — максимальное разрешение.

**Тай-брейки при равном времени снимка** (по возрастанию приоритета выбора):
1. «Копийные» маркеры имени (` (Copy 2)`, ` (1)`, ` — копия`, ` - Copy`,
   `-edited`) проигрывают чистому имени;
2. **ранний ctime** — лечит кейс «скопировали и переименовали в короткое имя
   (`2.jpg`), json-файла нет»: копия наследует mtime источника (время снимка
   выходит равным), но её ctime = момент копирования, то есть ПОЗЖЕ, чем у
   оригинала. Раньше при полном тайе спор решался лексикографикой пути —
   и короткое имя `2.jpg` выигрывало у `IMG_…`; теперь выигрывает файл,
   созданный раньше;
3. лексикографически меньший путь — детерминизм последней инстанции.

Ни один эвристический сигнал не гарантирует 100%: в архивах встречаются
«фальшивые» времена и копии без каких-либо следов. Именно для таких случаев
в галерее есть ручные кнопки **⭐ «Это оригинал»** и **📋 «Это дубликат»** —
они выполняют обмен ролями с фактическим перемещением файлов (§5.1).

### 4.3 Папки групп и коллизии

Папка группы в trash называется по файлу-оригиналу: `_IMG_20260914_123649.jpg`
(префикс — `move.group_name_prefix`, `""` — без префикса; старый нейминг
`group_{id}` остаётся fallback). Риски нейминга закрыты:

* коллизии имён папок между группами — суффикс `__2`, `__3` (сравнение без
  учёта регистра, NFC: на macOS/Windows `IMG.jpg` и `img.jpg` — одно имя);
* запрещённые для Windows символы, зарезервированные имена (CON, NUL, COM1…),
  хвостовые точки/пробелы, стемы длиннее 100 символов — санитизируются;
* коллизии имён файлов внутри папки — суффикс `_1`, `_2` (детерминированная
  аллокация, её повторяет crash-recovery).

### 4.4 Точная верификация sha256

Перед переносом каждый дубликат группы хэшируется sha256 (чанковое чтение).
Равенство хэша оригинала = байт-в-байт копия независимо от phash и порога.
Точные копии помечаются в плане dry-run, в `info.txt` и `groups.info`
(`exact_kept_copies`, `dups_sha_checked`). Это только чтение — допустимо
и в dry-run.

### 4.5 Crash-recovery и статусы

Транзакция коммитится ПОСЛЕ файловых операций. Если движок упал между ними,
повторный `move` чинит состояние: файла нет в src, но он лежит в папке этой
группы (или legacy `group_{id}`) с ожидаемым именем и размером → `moved_to`
дописывается. Аллокация имён повторяется детерминированно с учётом уже
занятых слотов — одноимённые дубликаты не «приклеиваются» к одному файлу.

Перенесённые/исчезнувшие файлы: строки в `files` НЕ удаляются, а получают
`status='moved'` (история групп и галерея сохраняются), их хэши удаляются,
чтобы дубликаты не находились повторно. Вернувшийся на то же место файл
переиндексируется обратно в `ok`.

## 5. Ручные операции из UI и обслуживание (`engine/webops.py`)

Все операции согласованы с инвариантами move-этапа и журналируются в `events`.
В UI они **запрещены, пока движок работает** (по `status.updated_at`).

### 5.1 Кнопки галереи (под каждой картинкой)

* **⭐ «Это оригинал»** — файл возвращается на исходное место (если был
  в trash), текущий оригинал группы переносится в папку группы, роли
  меняются, `groups.kept_path` обновляется. Фактический обмен ролями.
* **📋 «Это дубликат»** — файл переносится в папку группы в trash. Если
  это был оригинал — новый выбирается автоматически по текущему `keep_by`
  (и его можно тут же переназначить ⭐).
* **↩️ «Вернуть»** — перенесённый файл возвращается на исходное место
  (роль остаётся «дубликат»: следующий `move` перенесёт снова; ⭐ назначит
  оригиналом). Если исходный путь занят — файл кладётся рядом с суффиксом
  `_restored`, путь в БД обновляется.
* **🗑️ «Удалить»** — удалить файл с диска (из trash или src) и вычистить
  его строки из БД. Необратимо; по умолчанию требует подтверждения
  (`ui.confirm_delete_files`).
* **ℹ️ «Свойства»** — модальное окно: тип, размеры, камера, выдержка,
  диафрагма, ISO, вспышка, замер, фокусное, дата съёмки (из `files.exif`)
  + дублирующий набор кнопок ⭐📋↩️🗑️.

После каждой операции info.txt папки группы переписывается под фактическое
состояние (или пустая папка удаляется) — crash-recovery не ломается.

### 5.2 Отмена переносов и очистка

* **`undo` / «↩️ Отменить всё»** — все файлы с заполненным `moved_to`
  возвращаются на исходные места (занятые исходные пути → `_restored`),
  пустые папки групп удаляются. Если ВСЁ вернулось без ошибок — результаты
  и журнал очищаются (TRUNCATE `events, group_members, groups, analysis_runs,
  hashes, files`). При проблемах очистка ОТКЛАДЫВАЕТСЯ: исправьте причину
  и повторите undo — уже возвращённые файлы пропускаются. `undo --dry-run`
  показывает план без изменений.
* **`clean-db` / «💥 Очистить БД»** — очистить результаты всех прогонов и
  журнал; файлы на диске не трогаются. ВНИМАНИЕ: перенесённые файлы остаются
  в trash, а БД об их связи забывает — сначала делайте undo.

## 6. Настройки и их влияние на результат

| Настройка | Влияние |
|---|---|
| `scan.extensions`, `scan.recursive` | Какие файлы вообще попадут в индекс; исключённые форматы/папки дубликатами не ищутся |
| `scan.threads` | Скорость этапа scan (CPU/IO); на результат не влияет |
| `scan.read_exif` | Заполнение `files.exif` при прогоне (свойства в UI). false — ленивое чтение при открытии окна «Свойства» |
| `hash.hash_size` | Разрядность хэша: выше — точнее, но чувствительнее к «почти одинаковым» кадрам. Смена без `--force` создаёт хэши другой длины (несравнимы со старыми, анализируются раздельно) |
| `hash.hash_part_len` | Размер бакета: больше — полнее поиск, но медленнее (больше пар) |
| `analyze.threshold` | Чувствительность к изменённым дубликатам: 0 — только идентичные/повёрнутые, выше — агрессивнее (см. §3.2) |
| `move.mode` | auto — переносить всё; manual — только подтверждённое |
| `move.keep_by` | Кто останется в src как оригинал (§4.2); применяется на момент переноса, в т.ч. к уже готовым группам |
| `move.group_name_prefix` | Имена папок групп в trash |
| `move.dry_run` | Полная блокировка физического переноса |
| `ui.page_size` | Сколько групп показывать на странице галереи (нагрузка UI) |
| `ui.confirm_*` | Диалоги подтверждения для необратимых кнопок UI |

Приоритет источников: **CLI-флаги > settings.toml > дефолты**. Ошибки в файле —
понятное сообщение с номером строки/ключом, а не трейсбек. Запись из UI —
атомарная (tmp + fsync + os.replace), а если `settings.toml` примонтирован
одиночным файлом (rename поверх точки маунта даёт EBUSY) — автоматический
откат на запись на месте, ошибка «Device or resource busy» исключена.

## 7. Почему эти зависимости (`requirements.txt`)

* **streamlit** — тонкий веб-фронт: фрагменты (`st.fragment`) с автообновлением,
  кэш ресурсов (`st.cache_resource`), быстрое прототипирование UI к БД;
* **pillow** — декодирование изображений, `draft()` для JPEG, EXIF-повороты,
  чтение EXIF-тегов, миниатюры в UI;
* **imagehash** (+ **numpy**, **scipy**, **PyWavelets** — его зависимости) —
  `imagehash.phash`: DC-компонента DCT 8×8. Свои реализации не дали бы ничего,
  кроме риска ошибок;
* **psycopg[binary]** + **psycopg-pool** — PostgreSQL: серверные курсоры
  (потоковая обработка бакетов без RAM-выброса), `Json`-адаптер, пул для UI;
* **tomli-w** — запись TOML для сохранения настроек из UI (чтение — stdlib
  `tomllib` с Python 3.11+);
* pillow-heif — опционально (закомментирован): поддержка HEIC/HEIF.

## 8. Ограничения (осознанные)

* Пары, различающиеся первыми 16 битами хэша, не сопоставляются (бакетный
  trade-off); байт-в-байт копии при этом не теряются никогда (§3.2);
* phash — перцептивный: серии «почти одинаковых» кадров могут группироваться;
  регулируется `threshold`;
* время снимка без json-sidecar — эвристика ФС (§4.2): возможны неверные
  назначения оригинала на экзотических копиях; финальный инструмент — кнопки
  ⭐/📋 в галерее;
* векторизованное сравнение требует хэшей ≤ 64 бит (`hash_size ≤ 8`);
  больше — автоматический fallback на чистый Python (медленнее).
