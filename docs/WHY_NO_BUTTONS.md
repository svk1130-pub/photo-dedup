# WHY_NO_BUTTONS — почему в UI нет кнопки «Запустить движок»

> Запрос: «настоящие кнопки запуска движка из UI (через docker-сокет)».
> Решение: **не делаем (пока)** — такие кнопки ослабляют принцип тонкого клиента,
> заметно снижают безопасность стенда и не соответствуют модели исполнения Streamlit.
> Этот документ — подробное объяснение: что именно ломается, что уже существует
> вместо кнопок и как сделать «настоящую кнопку» правильно, если она однажды
> понадобится. Смежные документы: [ARCHITECTURE.md](ARCHITECTURE.md),
> [UI_DESIGN.md](UI_DESIGN.md).
>
> **Обновление 1.5.0 (Ф1): кнопка появилась — «▶️ Запустить прогон» на Мониторе —
> но построена по схеме §5 (очередь jobs в PostgreSQL + сервис runner), БЕЗ
> docker-сокета даже в runner'е. Разделы 1–4 сохраняют силу: сокет в web
> по-прежнему отвергнут.**
>
> **Обновление 1.6.0 (Ф2): в очереди — все длинные команды** (кнопки
> ▶️ Полный прогон / 🔍 Скан / 🧠 Анализ / 📦 Перенос / ↩️ Undo на Мониторе),
> stale-детекция выполняется и из UI (периодический reap + подпись
> «прогон оборвался»), история очереди ограничена retention'ом
> (`RUNNER_RETAIN_JOBS`, по умолчанию 200). Схема не изменилась.
>
> **Обновление 1.7.0 (Ф3): отложенный запуск** — селект «Когда запускать»
> ставит задание с `jobs.scheduled_at` («не раньше»); runner не менялся
> (до срока `claim_next` возвращает None), над очередью — «▶️ Сейчас» /
> «⏰ +1 ч» / «✖ Отменить». Тонкий клиент не ослаблён: очередь по-прежнему
> INSERT + NOTIFY, отмена — UPDATE строки, никаких процессов из UI.
>
> **Обновление 1.8.0 (Ф3-хвост)**: «Своё время…» — точные ДАТА и время
> (календарь от сегодняшнего дня); прошедший момент не переносится молча,
> а даёт предупреждение и блокирует кнопки. По-прежнему INSERT в jobs +
> UPDATE строки при переносе — никаких процессов из UI.
>
> **Обновление 1.9.0**: то же правило — и для терминала: `engine schedule
> JOB --at/--delay` ставит отложенное задание в ту же очередь (INSERT +
> NOTIFY, выполняет runner). CLI — клиент очереди, без процессов; runner
> и БД не менялись.
>
> **Обновление 1.10.0**: полировка очереди — и снова только флаги и строки в
> БД: глобальная пауза (`status.runner_paused` — claim_next молчит, задания
> ждут), причина остановки (`jobs.stop_reason`: Стоп/сигнал/отмена/обрыв —
> видно в истории) и интерактивная история (удаление записи/очистка —
> DELETE строки). Из UI по-прежнему не запускается и не останавливается
> ни один процесс.
>
> **Обновление 1.11.0**: и косметика не меняет принципа — переключатель
> тёмной/светлой темы в сайдбаре это CSS-инжекция и флаг в session_state /
> query-параметре адреса страницы; никаких процессов и новых прав у web.

## 1. Что предлагалось

Кнопки «Запустить scan / analyze / move / run» на странице «Монитор», которые
запускают контейнер движка **из web-контейнера** через примонтированный
`/var/run/docker.sock` (docker SDK для Python либо вызов `docker compose run ...`
изнутри контейнера web).

Сейчас движок запускает человек из терминала хоста:

```bash
docker compose run --rm engine run
```

а UI показывает готовую команду (баннер, «⌨️ Быстрые команды», информер
«что делать дальше») и умеет всё, что не требует владения процессом: писать
флаг остановки, выполнять точечные файловые операции, undo и очистку БД.

## 2. TL;DR — три причины сказать «нет»

1. **Безопасность.** `/var/run/docker.sock` внутри web-контейнера — это
   эквивалент root-доступа ко всему хосту. При этом web — самое «мягкое» звено
   стенда: он парсит пользовательский ввод, декодирует изображения из архива
   (Pillow), тянет наибольшее количество сторонних зависимостей.
2. **Архитектура.** UI перестаёт быть тонким клиентом («читать БД, писать флаги,
   точечные файловые операции») и превращается в оркестратор процессов — роль,
   которую в проекте уже выполняют docker compose + терминал человека.
3. **Модель исполнения Streamlit.** UI-процесс непригоден для надзора за
   дочерним процессом, работающим часами (прогон архива до 3 ТБ): закрытая
   вкладка, реран скрипта или рестарт контейнера web осиротят или потеряют
   процесс, а состояние запуска умрёт вместе с памятью сессии.

## 3. Подробный разбор

### 3.1 docker-сокет = root на хосте

* Docker API, доступный через сокет, позволяет запускать контейнеры с любыми
  маунтами (классика: `-v /:/host`) — то есть любой процесс с доступом к сокету
  получает root на хосте. Это не «уязвимость», а документированная семантика
  Docker: сокет и есть полный контроль над демоном.
* Web — наименее защищённая поверхность из трёх контейнеров: Streamlit
  исполняет код приложения и виджетов, обрабатывает изображения из архива
  (парсеры Pillow/HEIF — регулярный источник CVE), зависит от большого дерева
  пакетов. Сегодня компрометация web ограничена: доступ к БД и rw-маунты
  `src`/`trash`. С сокетом она становится равной компрометации хоста и всех
  контейнеров стека — цена одной CVE в зависимости возрастает на порядок.
* Конфликт с non-root. Проект намеренно работает под `appuser` (uid 1000,
  см. Dockerfile и README §7), а сокет на хосте обычно принадлежит
  `root:docker` с GID, различающимся между машинами (999, 998, 42…).
  «Настоящая кнопка» потребует либо запустить web от root, либо подбирать
  GID под конкретный хост — оба варианта ломают переносимость, которую
  заявляет документация (maунты с правами хоста, `chown 1000:1000`).
* Добавление `docker` CLI и docker SDK в образ web увеличивает поверхность
  атаки и размер образа ради функции, которая дублирует терминал хоста.

### 3.2 UI из «тонкого клиента» становится оркестратором

Правила тонкого клиента зафиксированы в UI_DESIGN.md §1 и докстринге
`web/app.py`: никаких процессов; никакого состояния рабочего процесса в
памяти UI; всё, что должно пережить рестарт web, живёт в PostgreSQL или в
`settings.toml`; цель — реран UI < 300 мс. Кнопка запуска через сокет
нарушает их все одновременно:

* появляется **состояние запуска** (PID контейнера, exit code, признаки
  рестарта, хвост логов), которое нужно где-то хранить. Единственный носитель,
  доступный UI, — память процесса Streamlit, умирающая при каждом деплое или
  `docker compose restart web` (`restart: unless-stopped` гарантированно
  переживёт кнопку, а запущенный ею процесс — нет);
* UI принимает обязанности **супервизора**: следить, жив ли контейнер,
  обрабатывать падения, зомби-процессы, повторный запуск. Сегодня это
  штатно делают docker compose и терминал — наблюдаемо и без кода;
* вариант «запустить `docker compose run` изнутри web» требует ещё и
  compose-контекст внутри контейнера (compose-файл, `.env`, CLI) — два
  дополнительных маунта и зависимость, окончательно размывающие границу
  «web ничего не знает об инфраструктуре»;
* растёт логика, которую нужно тестировать: обработка «сокет недоступен»,
  «GID не совпал», «демон перезапустился», «контейнер завис» — каждая ветка
  воспроизводится только на конкретном хосте.

### 3.3 Модель исполнения Streamlit не рассчитана на долгоживущие процессы

* Streamlit перезапускает весь скрипт при каждом взаимодействии; жизненный
  цикл фоновых потоков привязан к сессии браузера. `st.fragment(run_every=…)`
  решает задачу «тикать UI», но не задачу «растить дочерний процесс часами».
* Пользователь закрыл вкладку — сессия закрыта. Кто дождётся `engine run`,
  рассчитанного на часы? Осиротевший процесс продолжит работать, но UI про
  него больше не знает, а новый реран честно покажет «движок не запущен» —
  UI и реальность расходятся.
* Несколько вкладок/браузеров — несколько «кнопок». Guard `is_working` в БД
  (окно 15 с по `status.updated_at`) — консультативный и рассчитан на то, что
  запускает человек: два `docker compose run`, стартовавшие с разницей в
  секунды из разных сессий, оба пройдут мимо него и начнут гонку за блоки
  этапа move и имена в trash. Сегодня конкурентность видима (два терминала
  = два запуска, человек это осознаёт); кнопка прячет её за иконкой.

### 3.4 Эксплуатация и диагностика

* Команда в терминале: видна в shell-history, её stdout/stderr — прямо перед
  глазами, состояние — в `docker compose ps`. Клик в UI: логи движка падают в
  stdout web-контейнера вперемешку с логами Streamlit (`docker compose logs
  web`), exit-код некому показать, ошибка «Permission denied» на сокет выглядит
  загадочным PermissionError в браузере.
* События «кто запустил движок» пришлось бы выдумывать: журнал `events`
  писали бы две стороны (UI «запустил», движок «работает»), и рассинхрон
  между ними — вопрос времени. Сейчас единственный источник истины о запуске —
  сам движок, пишущий в `status`/`events` из своего процесса.

### 3.5 Портируемость

* Сокет — особенность Docker CE на конкретном хосте. rootless-docker, podman,
  k8s — другие схемы, где маунт демона либо невозможен, либо запрещён политиками;
  монтирование `docker.sock` в под — общепризнанный анти-паттерн.
* README и ARCHITECTURE.md заявляют: «движок можно запускать как угодно» —
  из venv без docker, через compose, на любой машине с PostgreSQL. Сокетная
  кнопка навсегда привязывает UI к одной среде исполнения.

## 4. Что есть вместо этого (уже работает)

Принцип: **UI может всё, что не требует владения процессом** — и это всё
реализовано. Не сделано ровно одно действие — «нажать Enter за человека».

| Сценарий | Как делается сейчас |
|---|---|
| Запустить полный цикл / отдельный этап | Баннер + блок «⌨️ Быстрые команды» (`st.code`, копирование в один клик) → вставить в терминал хоста |
| Остановить движок | Кнопка «Стоп» в UI: пишет флаг `stop_requested` в БД — работает **без** сокета, потому что это флаг, а не процесс |
| Видеть прогресс | Фрагмент «Монитор» читает `status` (этап, X из Y, скорость, ETA) |
| Отменить все переносы | «↩️ Отменить всё» = `webops.undo_all`: БД + маунты, без процессов |
| Очистить результаты | «💥 Очистить БД» = `engine clean-db`: TRUNCATE результатов и журнала |
| Успеть скопировать команду | Информер «что делать дальше» с готовой командой и счётчиками (manual-режим) |

Разница между «кнопкой» и «скопированной командой» — одно нажатие Enter.
Разница в рисках — сокет с root-правами в самом уязвимом контейнере.

## 5. Если кнопка однажды станет действительно нужна — правильные схемы

> **Статус: РЕАЛИЗОВАНО в 1.5.0 (Ф1) и 1.6.0 (Ф2) — схема №1, вариант A: очередь jobs
> в PostgreSQL + in-process runner. docker-сокет не используется НИГДЕ — даже
> runner'у он не понадобился (в исходной редакции этого раздела предполагался
> сокет в sidecar-контейнере; при реализации выбрали решение лучше: runner — тот же
> образ/маунты/код, что у engine, просто вечный цикл вместо одноразовой команды).**

Общее у всех схем: **web не получает сокет** — он лишь просит внешний,
минимально привилегированный компонент запустить процесс.

1. **Очередь задач в БД + runner (вариант A — реализовано в 1.5.0/1.6.0).** Таблица
   `jobs (id, command, params, state, requested_at, taken_at, heartbeat_at,
   runner_id, exit_code, error, result)`. UI только вставляет строку
   (INSERT + `pg_notify`) — остаётся тонким. Контейнер `runner` — тот же образ,
   маунты и env, что у engine (`restart: unless-stopped`), БЕЗ docker-сокета:
   забирает задание атомарно (`SELECT … FOR UPDATE SKIP LOCKED` + single-flight
   guard по `status.stage`) и выполняет команду движка **in-process** — тот же
   код, что у CLI, без subprocess и повторного argparse. В очередь ставятся ВСЕ
   длинные команды (1.6.0): `run`, `scan`, `analyze`, `move`, `undo` (undo —
   только через подтверждение в UI). Мгновенное пробуждение —
   LISTEN/NOTIFY, фоллбэк — опрос раз в несколько секунд; живость выполнения —
   heartbeat в jobs (отдельный поток); зависшие задания помечаются stale
   (crash-recovery на рестарте runner'а И периодически из UI — подпись
   «прогон оборвался»; штатный Resume команд продолжит работу). История
   очереди ограничена retention'ом: runner после каждого finish удаляет
   задания сверх последних `RUNNER_RETAIN_JOBS` (по умолчанию 200), а
   «💥 Очистить БД» вычищает очередь целиком.
   Аудит — events + история jobs; «Стоп» работает как раньше (тот же флаг
   `status.stop_requested`). CLI `docker compose run --rm engine …` не менялся.
   Почему джобы в PostgreSQL, а не Redis: задание — durable-данные (история
   прогонов), как events, а не транзитное сообщение; SKIP LOCKED + NOTIFY
   покрывают потребность полностью, а стек не получает +1 компонент.
2. **Движок-демон.** Перевести engine в `restart: unless-stopped` с внутренним
   циклом «ждать флаг `run_requested` в `status`» — UI по-прежнему пишет только
   флаг. Минус: движок перестаёт быть «прогоняемой вручную командой»,
   меняется модель crash-recovery — это большой редизайн, требующий
   отдельного раунда обсуждения.
3. **systemd-юнит на хосте + мини-API.** UI вызывает крошечный HTTP-агент на
   хосте, который делает `systemd-run` конкретного юнита. Тоже выносит
   docker-контроль из web, но добавляет компонент на хосте.

## 6. Когда стоит вернуться к вопросу

* запуск прогонов с телефона/планшета или headless-сервер без терминала —
  **рутинно**, а не разово;
* многопользовательский режим, где запуск через терминал неудобен
  организационно.

При наступлении любого из условий реализуем схему №1 (job-runner) — это
изолированный раунд: одна таблица, один контейнер, кнопка в UI, тесты.

> **Реализовано в 1.5.0 (Ф1)**: таблица jobs, сервис runner, кнопка
> «▶️ Полный прогон», тесты (smoke §10, integ §18).
> **Реализовано в 1.6.0 (Ф2)**: кнопки scan/analyze/move/undo, stale-детекция
> в UI (reap + подпись «прогон оборвался»), retention истории очереди
> (smoke §11, integ §18g–h).
> **Реализовано в 1.7.0 (Ф3)**: отложенный запуск — `jobs.scheduled_at`,
> селект «Когда запускать» на Мониторе, перенос/отмена queued-задания
> (smoke §13, integ §18j); в 1.8.0 «Своё время…» умеет точную дату
> (календарь + валидация прошедшего момента); в 1.9.0 то же умеет CLI —
> `engine schedule JOB --at/--delay` (smoke §15, integ §18k). Схема №1
> не менялась с 1.5.0: всё те же одна таблица, один сервис и тонкий
> клиент — ни docker-сокета, ни subprocess.

## 7. Итог

| Вопрос | Ответ |
|---|---|
| Ослабляют ли docker-сокетные кнопки принцип тонкого клиента? | Да: UI получает владение процессами и состояние вне БД (§3.2–3.3) |
| Влияют ли они на безопасность? | Сокет = root на хосте; web — самое уязвимое звено; конфликт с non-root (§3.1) |
| Что делать сейчас? | Ничего: команды уже в UI, копируются в один клик; Стоп/undo/очистка работают без процессов (§4) |
| Когда будет кнопка? | Есть с 1.5.0, в 1.6.0 — для всех длинных команд: кнопки Монитора → очередь jobs → runner (вариант A), сокет не нужен нигде (§5–6) |
