# UI_DESIGN: Streamlit-фронт для высоконагруженного движка

> Как web-контейнер остаётся «тонким клиентом» (цель — реран UI < 300 мс),
> когда движок на полной скорости индексирует архив до 3 ТБ. Здесь — конкретные
> механизмы и фрагменты кода; общий контекст — [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. Постановка проблемы

Движок — долго работающий CPU/IO-процесс (scan: сотни файлов/с, analyze:
бакетные сравнения, move: дисковые операции). Наивный Streamlit-фронт при этом
деградирует по трём причинам: (а) каждый клик реранит ВЕСЬ скрипт; (б) тяжёлые
SELECT-ы блокируют соединения; (в) отрисовка изображений убивает браузер.
Дизайн UI строится вокруг четырёх правил-запретов (см. докстринг `web/app.py`):

1. **никаких subprocess движка** — UI и движок общаются только через
   PostgreSQL (флаги, статусы, события) и файл настроек;
2. **никаких обходов файловой системы** — единственное исключение (1.4.0):
   точечные файловые операции `engine/webops.py` по путям, взятым из БД
   (⭐/📋/↩️/🗑️/undo), без единого обхода дерева;
3. **никаких запросов без LIMIT** — всё, что может расти (файлы, группы,
   члены групп, журнал), идёт через пагинацию/агрегаты/хвосты;
4. **никакой обработки изображений кроме миниатюр** — исходник никогда
   не уходит в `st.image` без даунскейла.

## 2. Изоляция тяжёлых вкладок: `st.fragment`

Монитор и журнал — автообновляемые фрагменты; они реранятся **отдельно от
страницы**, и их тики не перерисовывают галерею/сайдбар:

```python
@st.fragment(run_every=f"{MONITOR_REFRESH_SEC}s")
def monitor_fragment(settings: Settings) -> None:
    row = engine_row()          # 1 запрос к status
    ...
    st.caption(f"фрагмент обновлён за {(time.perf_counter() - tf) * 1000:.0f} мс …")
```

* интервал автообновления — настройка `ui.refresh_sec` (1–60 с), читается
  один раз на процесс (`_read_refresh_at_import`: фрагменты создаются при
  импорте);
* внутри фрагмента — 3–4 коротких запроса (status, агрегаты по последнему run);
  тяжёлые операции отображаются так же (прогресс/ETA считаются в БД-статусе
  движком, UI только читает).

## 3. Пул соединений и дисциплина запросов

```python
@st.cache_resource(show_spinner="Подключение к базе данных…")
def get_pool() -> ConnectionPool:
    return ConnectionPool(conninfo=DSN, min_size=1, max_size=5, open=True,
                          name="web-pool", kwargs={"row_factory": dict_row},
                          check=ConnectionPool.check_connection)

def q(sql, params=(), *, fetch=True):
    with get_pool().connection() as conn:
        with conn.cursor() as cur:
            cur.execute(sql, params)
            return cur.fetchall() if fetch else None
```

* `st.cache_resource` — один пул на процесс (не на сессию/реран);
  `max_size=5` — намеренно мало: UI не должен выжать БД у движка;
* все запросы приложения проходят через `q()` — легко проверить, что нет
  неограниченных выборок; размер каждого результата ограничен конструкцией
  (`LIMIT/OFFSET`, `ANY(массив id страницы)`, агрегаты `count/sum`);

## 4. Галерея: пагинация и батч-выборка членов

```python
page_rows = q("SELECT id, member_count, total_size, kept_path, confirmed, info "
              "FROM groups WHERE run_id=%s ORDER BY total_size DESC, id "
              "LIMIT %s OFFSET %s", (lr["id"], page_size, page * page_size))
ids = [g["id"] for g in page_rows]
member_rows = q("SELECT gm.group_id, gm.file_id, gm.role, gm.moved_to, f.path, "
                "f.size, f.mtime, f.width, f.height "
                "FROM group_members gm JOIN files f ON f.id=gm.file_id "
                "WHERE gm.group_id = ANY(%s) ORDER BY …", (ids,))
```

* страница = `ui.page_size` групп (5–100); члены ВСЕХ групп страницы —
  ОДНИМ батч-запросом `ANY(ids)` (с 1.3.0 — устранён N+1);
* страницы-кандидаты не перечитываются до клика — навигация стоит двух
  запросов на показ.

## 5. Миниатюры: ленивый дисковый кэш (`web/thumbs.py`)

```python
key = hashlib.sha256(str(p).encode()).hexdigest()[:32]
cache_file = CACHE_DIR / f"{key}_{size}.jpg"
if cache_file.is_file():
    return cache_file.read_bytes()          # попадание в кэш — один read
with Image.open(p) as img:
    if (img.format or "").upper() in ("JPEG", "MPO"):
        img.draft("RGB", (size, size))      # черновое декодирование — дёшево
    img = ImageOps.exif_transpose(img)
    img.thumbnail((size, size))
    ...
tmp.replace(cache_file)                     # атомарная замена (параллельные сессии)
```

* миниатюра ~400 px в JPEG q=80: исходник 3 ТБ-архива никогда не передаётся
  в браузер; повторный просмотр — чтение файла кэша (named volume);
* ключ — sha256 пути: перенос файла (⭐/↩️) просто создаёт новый ключ,
  старые записи безвредны;
* любые ошибки чтения/декодирования → `None` → подпись «🚫 не удалось
  показать» вместо падения страницы.

## 6. «Живой» мониторинг без subprocess: флаги и статус

* **Запуск прогонов (1.5.0 Ф1 + 1.6.0 Ф2; отложенный — 1.7.0 Ф3)** — кнопки на
  Мониторе ставят задания в очередь `jobs` (INSERT + `pg_notify`; дубль той же
  команды отсекается частичным уникальным индексом) — выполняет их сервис
  `runner`: «▶️ Полный прогон» (`run` = scan→analyze→move), «🔍 Скан»,
  «🧠 Анализ», «📦 Перенос» и «↩️ Undo» (у Undo — обязательное двухфазное
  подтверждение: «✅ Да, вернуть файлы» / «❌ Отмена»). Над кнопками — селект
  **«Когда запускать»**: Сейчас (по умолчанию, прежнее поведение) / через
  30 мин / 1 ч / 3 ч / сегодня в 03:00 / завтра в 03:00 / своё время… —
  применяется к любой кнопке: задание ставится с `scheduled_at`, и runner
  не берёт его до срока (точность ≈ 2 с; пояс пресетов — env `TZ` web,
  по умолчанию Europe/Moscow). «Своё время…» (1.8.0) — точные дата и время:
  календарный `st.date_input` (ДД.ММ.ГГГГ, `min_value` = сегодня) рядом с
  `time_input`; прошедший момент (сегодня, время меньше текущего) НЕ
  переносится молча, а даёт предупреждение «⏰ Выбранный момент уже в
  прошлом» и блокирует все кнопки запуска — у явной даты выбор явный.
  Пока runner выполняет задание или в очереди
  есть «созревшее», кнопки заблокированы (single-flight); одно ОТЛОЖЕННОЕ
  задание немедленному запуску других команд не мешает. Равнозначный путь —
  терминал: баннер и «⌨️ Быстрые команды»
  показывают `st.code("docker compose run --rm engine run")`.
* **Блок очереди на Мониторе** — под кнопками: список queued-заданий
  («⏳ #id `команда` — runner заберёт в ближайшие секунды» или «⏰ #id
  `команда` — отложено до DD.MM HH:MM (через 3 ч 05 мин)») с действиями на
  каждое: «▶️ Сейчас» (снять отсрочку), «⏰ +1 ч», «✖ Отменить» (не начатое
  задание → stopped «не начато»; файлы не затрагиваются, слот той же команды
  освобождается) — `jobs.reschedule`/`jobs.cancel_queued`; «🏃 Runner
  выполняет задание #id (взял HH:MM:SS)» и история последних 5 заданий
  (state, exit code, длительность, первые 90 символов ошибки). Живёт в том же
  автообновляемом фрагменте (раз в `ui.refresh_sec`), выборка — агрегаты + LIMIT.
  **Stale-детекция из UI (1.6.0):** при каждом обновлении фрагмент выполняет
  `reap_stale` (running-задание с протухшим heartbeat → stale; порог
  `RUNNER_STALE_SEC`, тот же, что у runner'а) и показывает предупреждение
  «⚠️ Прогон оборвался» с Resume-подсказкой (запустить этап заново — scan/move
  продолжат с места остановки). История очереди ограничена retention'ом
  (`RUNNER_RETAIN_JOBS`, по умолчанию 200) и вычищается «💥 Очистить БД».
* **Остановка** — UI пишет флаг, движок (CLI или runner) его опрашивает
  (`db.request_stop` / `ctx.should_stop()`): мягкая остановка после текущего
  файла/батча, данные не страдают; задание получает state=`stopped`.
* **Прогресс** — движок обновляет `status` (этап, processed/total, скорость,
  текущий файл) раз в батч/0.5 с; UI читает. ETA считается в тех же единицах,
  что и скорость (бакетов/с для analyze, файлов/с для scan/move).

## 7. Ручные операции (1.4.0): как сделаны безопасно

**Guard параллельности.** Все мутирующие кнопки (файловые операции, undo,
очистка БД) отключены, пока движок работает:

```python
row = engine_row()                       # (updated_at > now()-15s) AND stage IN (scan,analyze,move)
locked = is_working(row)
...
if b_star.button("⭐", disabled=locked or (m["role"] == "kept" and not m["moved_to"]), ...):
    _do_action(settings, webops.star_as_original, fid, gid=gid, ...)
```

**Тонкие операции вместо толстых.** `_do_action` открывает соединение из пула
на одну операцию; сама операция — `engine/webops.py` (1–2 `shutil.move`/
`os.unlink` по путям из БД + короткая транзакция + запись в `events`).
Никаких «перепроверить весь архив» из UI.

**Подтверждения.** Необратимые действия защищены двухфазным подтверждением
in-place (`_confirm_button`: кнопка → «⚠️ Точно?» → «✅ Да / ❌ Отмена» на
`session_state`); для 🗑️ под каждой картинкой — тот же паттерн (🗑️ → ❗/❌).
В модальном окне «ℹ️ Свойства» подтверждение 🗑️ остаётся ВНУТРИ окна (1.4.3):
диалог работает как фрагмент (перерисовка по клику без полного rerun),
поэтому вооружение и отмена выполняются без `st.rerun` — окно не закрывается;
полный rerun происходит только после самого действия. Состояния подтверждения
разделены: сетка — `delarm_*`, окно — `dlgarm_*` (сбрасывается при новом
открытии окна). Диалоги можно отключить настройками `ui.confirm_*`
(по умолчанию включены).

**Модальное окно свойств** — `@st.dialog`: EXIF из `files.exif`; если пусто —
ленивое чтение заголовков с диска ТОЛЬКО при открытии окна с записью в БД
(кэш): на скорость галереи не влияет вовсе. Кнопки в окне — ⭐ 📋 ↩️ 🗑️;
кнопки ℹ️ в окне НЕТ (1.4.3): она открывала то же окно изнутри его самого.

**Ключи виджетов.** Диалог рендерится параллельно с основной страницей, поэтому
кнопки в диалоге получают префикс `key_prefix="dlg_"` и флаг `in_dialog=True`
— иначе DuplicateWidgetID и ложная кнопка ℹ️ внутри окна.

## 8. UX-детали, влияющие на воспринимаемую скорость

* **Expander групп сохраняет состояние.** Streamlit-раскрывашки теряют
  открытое состояние, когда дерево выше меняется (например, после удаления
  файла). Поэтому открытое состояние группы хранится явно:
  `st.session_state[f"grp_open_{gid}"]=True` → `st.expander(..., expanded=...)`
  — после любой операции группа остаётся раскрытой.
* **Галерея: автообновление после прогона (1.7.0).** Постоянный поллинг
  галереи НЕ включён (при больших архивах перерисовка сотен миниатюр по
  таймеру тяжела для браузера). Вместо него фрагмент Монитора (он и так
  опрашивает БД каждые `ui.refresh_sec` независимо от активной вкладки)
  следит за переходом «движок/задание заняты → освободились»
  (`session_state["prev_engine_live"]`) и на границе делает ОДИН полный
  `st.rerun(scope="app")` — галерея перечитывает данные, кнопки
  разблокируются. Кнопка «🔄 Обновить» остаётся для CLI-прогонов и ручных
  операций (⭐/📋/↩️/🗑️ сами делают rerun, как и раньше).
  С 1.7.1 edge-детект выполняется В НАЧАЛЕ фрагмента, до отрисовки элементов:
  полный rerun из середины фрагмент-рана дублировал клиенту хвост фрагмента
  (задвоение блоков «Опасная зона» после Прогона/Скан).
* **Опасные зоны по режиму (1.7.1).** «⚠️ Подтверждение переноса (manual)»
  показывается только при `move.mode=manual` (в auto move переносит все
  группы, подтверждения ни на что не влияют); «🧨 Обслуживание БД» —
  в обоих режимах (`_db_ops_block`).
* **Информер «что делать дальше».** В manual-режиме подтверждение групп —
  только половина работы: физический перенос делает `engine move`. Монитор
  и галерея показывают текущее состояние («подтверждено X из Y», «перенесено
  файлов N») и следующий шаг с готовой командой.
* **Метрика «UI rerun, мс»** в сайдбаре — wall-time полного рерана
  (`time.perf_counter`), avg(10)/max(30) по сессии; фрагменты в замер не
  входят (их длительность видна каптионом внутри). Ориентир < 300 мс при
  работающем движке; превышение — сигнал проверить, не заменили ли запросы
  на неограниченные.

## 9. Чего UI сознательно НЕ делает

* не запускает/не убивает процессы движка (нет docker-socket, нет subprocess);
  задание «▶️ Полный прогон» — это строка в очереди `jobs`, а исполняет его
  отдельный контейнер `runner` (или человек через CLI). Почему запуск не через
  docker-сокет — разбор: [WHY_NO_BUTTONS.md](WHY_NO_BUTTONS.md) §5 (с 1.5.0
  схема реализована — вариант A, in-process runner без сокета);
* не выполняет запросы вне `q()` и вне пула;
* не обходит файловую систему (кроме точечных webops-операций и ленивого
  чтения EXIF при открытии окна свойств);
* не хранит состояние рабочего процесса в памяти UI: всё, что должно
  пережить перезапуск web, живёт в PostgreSQL (`status`, `events`, `groups`,
  `jobs`) или в `settings.toml`.
