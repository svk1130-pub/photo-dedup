# Photo Dedup — движок поиска дубликатов + тонкий Streamlit-UI

Готовое Python-приложение для поиска и перемещения **изменённых / повёрнутых / зеркальных**
дубликатов фотографий в больших архивах (до 3 ТБ, сотни тысяч файлов, вложенные подпапки).

Приоритет проекта — **прототип для теста Streamlit как фронтенда к долго работающему
высоконагруженному бэкенду**: вся тяжёлая логика живёт в отдельном CLI-процессе,
Streamlit — тонкий клиент, который только читает состояние из PostgreSQL и пишет
команды-флаги. UI остаётся отзывчивым при полной загрузке движка (ориентир —
реран UI < 300 мс, см. раздел «Измерение производительности»).

Основной сценарий: движок запускается из командной строки
(`docker compose run --rm engine run` или `python -m engine.cli run`), веб-интерфейс
открывается опционально — для мониторинга и управления. Движок корректно работает
при полностью закрытом UI.

---

## 1. Архитектура

Три независимых процесса (контейнера), общаются только через PostgreSQL:

```
┌─────────────────┐        ┌──────────────────────┐        ┌─────────────────┐
│  engine (CLI)   │        │  PostgreSQL 16 (db)  │        │  web (Streamlit)│
│  scan/analyze/  │──W──▶  │  files, hashes,      │  ◀──R──│  :8501, тонкий  │
│  move/run/stop  │──W──▶  │  groups, status,     │  ──W─▶ │  клиент, пул ≤5 │
│  ThreadPool×N   │        │  events, runs        │        │  флаги/настройки│
└─────────────────┘        └──────────────────────┘        └─────────────────┘
      ▲                        named volume pgdata            thumbs-cache volume
      └── запускается человеком: docker compose run --rm engine ...
          (без автозапуска и рестартов)
```

* **db** — `postgres:16-alpine`, healthcheck `pg_isready`, named volume `pgdata`.
* **engine** — CLI (`python:3.12-slim`, non-root). Не автозапускается, не рестартует:
  используется через `docker compose run --rm engine <команда>` или кнопками на
  вкладке «Монитор» (см. ниже).
* **web** — Streamlit `:8501`, `--server.headless=true`, healthcheck `/_stcore/health`,
  `restart: unless-stopped`. Управляет движком флагами в БД (`stop_requested`,
  `groups.confirmed`) и настройками; с 1.4.0 — по явному запросу пользователя —
  двумя ТОЧЕЧНЫМИ исключениями из «тонкости»:
  кнопки «Монитора» стартуют тот же CLI как subprocess внутри web-контейнера
  (`python -m engine.cli run|scan` — эквивалент `docker compose run` по эффекту:
  тот же образ, env и маунты; буквально `docker compose run` из UI потребовал бы
  проброса docker.sock — root-доступ к хосту), и `web/actions.py` возвращает/
  удаляет ОДИН файл из trash по кнопке в галерее (rw-доступ к фото).
  Групповые операции по-прежнему только у движка.

UI умеет помимо чтения: кнопка «Стоп» (флаг `stop_requested`), кнопки запуска
`run`/`scan` (subprocess), подтверждение групп для переноса в manual-режиме,
запись настроек в `settings.toml`, возврат/удаление одного перенесённого файла
(«↩️ Вернуть» / «🗑️ Удалить» в галерее, с диалогом), «Очистить все» (TRUNCATE
результатов) и очистку журнала. Всё остальное — только SELECT с LIMIT/агрегатами.

## 2. Quickstart

Требуется Docker Compose v2.20+ (используется `bind.create_host_path`).

```bash
cd photo-dedup

# 1. Хост-корень фото + настройки (создайте СВОИМ пользователем, см. §7 про права)
cp .env.example .env          # PHOTOS_ROOT=./photos — или ваш путь, напр. /home/me/myfotos
cp settings.example.toml settings.toml   # в [paths] укажите пути КАК НА ХОСТЕ:
                                         # src = "/home/me/myfotos/src"
mkdir -p photos/src photos/trash
# положите фотографии в photos/src (для быстрого теста можно сгенерировать набор, см. ниже)

# 2. Сборка и запуск БД + UI
docker compose build
docker compose up -d db web
# UI: http://localhost:9501 — запускать движок можно кнопками на вкладке «Монитор»

# 3. Тестовый набор с поворотами/отражениями (критерий приёмки №2):
docker compose run --rm --entrypoint python engine scripts/make_testset.py /photos/src/testset 5

# 4. Полный цикл: scan → analyze → move (с Resume)
docker compose run --rm engine run

# 5. Статус / мягкая остановка / возобновление
docker compose run --rm engine status
docker compose run --rm engine stop
docker compose run --rm engine run          # продолжит с места остановки

# 6. Остановить фоновые сервисы (данные в volume pgdata сохранятся)
docker compose down
```

Примечание о `stop`: флаг действует на **работающий** движок — он доделает текущий
файл/батч и остановится. При старте следующей рабочей команды флаг сбрасывается,
поэтому устаревший флаг не помешает будущим запускам.

Движок можно запускать и при закрытом UI, и поэтапно:

```bash
docker compose run --rm engine scan                     # только индексация
docker compose run --rm engine analyze                  # только поиск групп
docker compose run --rm engine move --dry-run           # план переноса
docker compose run --rm engine move                     # перенос (auto-режим)
docker compose run --rm engine move --move-mode manual  # только подтверждённые группы
docker compose run --rm engine run --dry-run --threads 4 --threshold 6
```

Флаги CLI **имеют приоритет** над settings.toml: `--threads`, `--threshold`,
`--dry-run`, `--move-mode`, `--keep-by`, `--force`, `--group-id`, `--settings`.

Локально без docker (нужны Python 3.12, PostgreSQL и `pip install -r requirements.txt`):

```bash
export PG_DSN=postgresql://photo:photo@localhost:5432/photo
export SETTINGS_PATH=./settings.toml
python -m engine.cli run
PYTHONPATH=. streamlit run web/app.py --server.headless=true
```

## 3. Настройки (settings.toml)

Читается стандартным `tomllib`, пишется `tomli-w`. Приоритет: **CLI-флаги >
settings.toml > дефолты**. Поставляется `settings.example.toml` с комментариями.

| Секция | Ключ | Дефолт | Смысл / когда применяется |
|---|---|---|---|
| `[paths]` | `src`, `trash` | `/photos/src`, `/photos/trash` | Архив и приёмник дубликатов — пути **КАК НА ХОСТЕ** (напр. `/home/me/myfotos/src`), редактируются из UI. В docker автоматически переводятся внутрь маунта `/photos` через `PATH_MAP_*` (корень — `PHOTOS_ROOT` в .env); путь вне корня — понятная ошибка при старте. Без docker — используются как есть. Валидация при старте: `trash` внутри `src` (или совпадение) → аварийный выход |
| `[scan]` | `extensions` | `.jpg .jpeg .png .webp .bmp .tiff` | Какие файлы индексировать |
| `[scan]` | `recursive` | `true` | Обходить подпапки |
| `[scan]` | `threads` | `8` | Потоки хэширования. Применится на этапе **scan** |
| `[scan]` | `batch_size` | `200` | Размер батча записи в БД (одна транзакция) |
| `[hash]` | `method` | `phash` | `imagehash.phash` |
| `[hash]` | `hash_size` | `8` | 64-битный хэш |
| `[hash]` | `hash_part_len` | `4` | Hex-символов на бакет (4 = 16 бит) |
| `[analyze]` | `threshold` | `4` | Макс. расстояние Хэмминга. Применится на этапе **analyze** |
| `[move]` | `mode` | `auto` | `auto` — все группы; `manual` — только `confirmed`. Применится на этапе **move** |
| `[move]` | `keep_by` | `capture` | Что считать оригиналом: `capture` — по времени снимка (см. §4), `size` (макс. размер), `pixels` (макс. разрешение) |
| `[move]` | `group_name_prefix` | `_` | Префикс имён папок групп в trash: `_IMG_20260914_123649.jpg` (имя строится по файлу-оригиналу; `""` — без префикса) |
| `[move]` | `conflict` | `suffix` | Коллизии имён файлов внутри папки группы: `_1`, `_2`…; коллизии имён самих папок групп — `__2`, `__3`… |
| `[move]` | `dry_run` | `false` | Dry Run главнее переноса: физически ничего не перемещается |
| `[ui]` | `page_size` | `15` | Групп на страницу галереи (применяется сразу) |
| `[ui]` | `refresh_sec` | `2` | Автообновление фрагментов (применяется после рестарта web) |
| `[ui]` | `confirm_delete_files` | `true` | Диалог «удалить безвозвратно?» перед удалением файла из trash (галерея, 🗑️); `false` — удаление сразу |
| `[ui]` | `confirm_clean_all` | `true` | Диалог перед «Очистить все» (результаты прогонов + журнал); `false` — сразу |
| `[ui]` | `confirm_clean_log` | `true` | Диалог перед очисткой журнала (🧹); `false` — сразу |

Движок **перечитывает настройки на границе этапов** (`run`: scan → analyze → move),
UI показывает эффективную конфигурацию и помечает в подсказках полей, когда
каждое изменение применится. Ошибки в файле — внятное сообщение с номером строки
(синтаксис) или ключом секции (типы), не трейсбек.

**Как UI пишет настройки (выбор маунта).** `settings.toml` — один host-файл,
примонтированный в оба контейнера:

* engine: `./settings.toml → /app/settings.toml` с флагом **`:ro`** — движок настройки
  только читает, случайно повредить файл он не может;
* web: тот же `./settings.toml → /data/settings.toml` **без `:ro`** — форма в сайдбаре
  пишет именно в него (читаем TOML → мерджим → пишем tomli-w).

Это даёт единственный источник правды: правки из UI мгновенно видны CLI-движку
на следующем этапе/запуске, ручные правки — видны UI. Нюансы: (а) при сохранении
из UI комментарии TOML теряются (ограничение tomli-w), а сама запись атомарна
(временный файл в том же каталоге + fsync + os.replace — движок, перечитывающий
настройки на границе этапов, всегда видит целостный файл, без разрыва на границе
записи) — образец комментариев живёт в `settings.example.toml`; (б) в compose включён `bind.create_host_path: false`,
поэтому если забыть `cp settings.example.toml settings.toml`, compose сразу
выведет понятную ошибку вместо тихого создания каталога; (в) если `settings.toml`
смонтирован в контейнер как **файловый** bind-mount, `os.replace` поверх
mountpoint невозможен ([Errno 16] Device or resource busy) — в этом случае запись
автоматически выполняется НА МЕСТО в тот же inode (с fsync): контейнеры,
маунтящие тот же host-файл, видят обновление, ошибка из 1.3.0 исключена.

**Пути на хосте (PATH_MAP).** Маунты docker нельзя менять на лету, поэтому
хост-корень фото задаётся один раз в `.env` (`PHOTOS_ROOT`, маунтится как
`/photos`), а подпапки `src`/`trash` — свободно редактируются из UI и в
`[paths]` в host-форме: `/home/me/myfotos/src` внутри контейнера превращается в
`/photos/src`. Путь вне `PHOTOS_ROOT` — ошибка валидации (и в UI при сохранении,
и при старте движка), а не молчаливое сканирование пустой папки. Без docker
(env не задан) пути используются как есть — удобно для локального запуска.

## 4. Как работает движок

### Этап 1 — scan (индексация)

* Рекурсивный `os.walk` с учётом `recursive`; пропускаются папка `trash`, скрытые
  директории и симлинки (защита от циклов).
* Общее число файлов-кандидатов (знаменатель прогресс-бара) считается в
  фоновом потоке параллельно с хэшированием — двойной обход дерева устранён;
  как только счёт готов, прогресс-бар и ETA появляются в статусе/UI.
* `ThreadPoolExecutor(threads)`: воркеры **только вычисляют хэши**, все записи в БД
  делает главный поток пачками `executemany` (batch_size) в одной транзакции —
  нет конкурентной записи, статус обновляется раз в батч.
* Для JPEG — `img.draft("RGB", (512, 512))` до декодирования (многократное ускорение);
  затем `ImageOps.exif_transpose` (Pillow сам EXIF-поворот не применяет).
* **Инвариантность к D4**: для каждого файла считаются 8 phash — по всем элементам
  группы D4: identity (исходное изображение — в `PIL.Image.Transpose` ровно 7 режимов,
  единичный элемент это картинка без трансформации), ROTATE_90/180/270,
  FLIP_LEFT_RIGHT, FLIP_TOP_BOTTOM, TRANSPOSE, TRANSVERSE. Никакой min-канонизации:
  композиция поворота и отражения не входит в набор из 5, зеркальные копии терялись
  бы. Все 8 вариантов — отдельными строками в `hashes`.
* **Resume**: файл пропускается, если в БД есть запись с тем же `(path, size, mtime)`
  и хэши на месте (учёт и ранее «битых» файлов — они не ретраятся каждый запуск).
  Изменившийся файл переиндексируется: сначала удаляются его старые строки хэшей.
  Принудительная переиндексация — `--force`.
* Битые файлы (в т.ч. `DecompressionBombError`, `UnidentifiedImageError`) получают
  `status='corrupt'` с текстом ошибки в `files.error`.
* **Остановка**: флаг `stop_requested` проверяется перед постановкой каждого файла;
  текущие in-flight файлы доделываются, батч коммитится, статус → `stopped`.
  SIGINT/SIGTERM обрабатываются так же (первый сигнал — мягкая остановка, второй —
  принудительный выход): `docker stop` и Ctrl+C не портят данные.

### Этап 2 — analyze (поиск групп)

* Бакеты по `hash_part` перебираются **потоковым серверным курсором**
  (`cursor(name=...)`, `itersize`) — один проход по `hashes`, ничего не тащится в RAM.
* Внутри бакета — попарное расстояние Хэмминга по полному phash (XOR + popcount;
  для 64-битных хэшей векторизовано numpy: `np.bitwise_count`). Пары считаются
  **2D-блоками** (строки × столбцы): память ограничена блоком ~1024×1024
  (десятки МБ) независимо от размера бакета — даже «плоский» бакет из десятков
  тысяч похожих кадров не приводит к OOM. Кандидат — ЛЮБАЯ пара вариантов
  (файл A, вариант i) ↔ (файл B, вариант j) с дистанцией ≤ threshold.
* **Смешанная длина хэшей** (после смены `hash_size` без `--force` старые
  8-байтные строки соседствуют с новыми): несравнимые хэши делятся на
  подгруппы равной длины и обрабатываются независимо — смешанный бакет не
  роняет analyze.
* Группы — транзитивное замыкание через **union-find** внутри бакета
  (A~B, B~C ⇒ одна группа, даже если A!~C).
* Результаты персистятся: `analysis_runs` + `groups`/`group_members`. Галерея всегда
  читает последний `run_id`; старые прогоны остаются в истории. Повторный анализ
  создаёт новый run, старые не трогает. Незавершённый (остановленный) run удаляется.
* **Документированный trade-off**: пары, чьи хэши различаются в первых 16 битах
  (hash_part_len=4 hex), не попадут в один бакет и не будут найдены — это осознанная
  плата за O(сумма квадратов размеров бакетов) вместо O(n²) по всему архиву.
* В `groups.info` сохраняются `min_distance` (мин. дистанция в группе), `kept_by`,
  threshold; `groups.kept_path` — предварительный оригинал по текущему `keep_by`.

### Этап 3 — move (перенос)

* Режим из настроек (`mode: auto|manual`), переопределяется `--move-mode` и
  переключателем в UI. **Dry Run всегда главнее**: фиксируется только план (events),
  физически ничего не переносится, **БД не меняется** — в том числе не
  восстанавливаются `moved_to` и не удаляются хэши отсутствующих файлов
  (эти действия попадают в план, как и перенос).
* **Точная верификация sha256**: перед переносом дубликаты группы хэшируются
  `sha256` (только чтение — допустимо и в dry-run). Равенство хэша оригинала —
  байт-в-байт копия независимо от phash и порога Хэмминга. В dry-run план
  помечает точные копии («· точная копия оригинала (sha256)»); после переноса
  счётчик пишется в `info.txt` и `groups.info` (`exact_kept_copies`,
  `dups_sha_checked`).
* «Оригинал» выбирается по текущему `keep_by`:
  * **`capture` (дефолт)** — по времени снимка. Иерархия источников для каждого
    файла (первый успешный выигрывает): ① Google-Takeout-sidecar `<файл>.json`
    рядом с файлом — `photoTakenTime` → `creationTime` (парсится только
    `timestamp`, локализованное `formatted` игнорируется; мусор/будущее —
    отбрасывается); ② файловая система — `min(birthtime, mtime)`: копии
    наследуют mtime источника, но получают новый birthtime, поэтому минимум
    двух времён ≈ время появления контента (на Windows роль birthtime играет
    `st_ctime`; если ФС не хранит birthtime — остаётся mtime); ③ mtime из БД.
    Тай-брейки при равном времени: «копийные» маркеры имени (` (Copy 2)`,
    ` (1)`, ` — копия`, `-edited`…) проигрывают чистому имени, далее —
    лексикографический путь. На этапе analyze роль kept — подсказка по mtime
    из БД; финальный выбор делается на move, когда доступна файловая система.
  * `size` — максимальный размер; `pixels` — максимальное разрешение.
* **Папка группы называется по оригиналу**: `_IMG_20260914_123649.jpg`
  (префикс настраивается `move.group_name_prefix`; прежний нейминг
  `group_{id}` остаётся fallback-ом для пустых имён). Риски нейминга закрыты:
  коллизии между группами — суффикс `__2`, `__3` (сравнение без учёта
  регистра, NFC — на macOS/Windows `IMG.jpg` и `img.jpg` одно имя);
  запрещённые для Windows символы (`< > : " / \ | ? *`, управляющие) и
  зарезервированные имена (CON, NUL, COM1…) санитизируются; хвостовые
  точки/пробелы срезаются; стем длиннее 100 символов обрезается. Папки,
  созданные прежними прогонами (в т.ч. старые `group_N`), учитываются и не
  переименовываются.
* Перенос через `shutil.move` (src и trash могут быть на разных ФС);
  коллизии имён файлов внутри папки группы — суффикс `_1`, `_2`…; рядом
  пишется `info.txt`: исходные пути, размеры, что оставлено, критерий
  оригинала, время снимка и его источник (для capture), порог, дата.
* После переноса обновляются `group_members.moved_to/moved_at` и `groups.kept_path` —
  галерея показывает новое расположение, а не мёртвые пути.
* В manual-режиме переносятся только группы с `confirmed = true` (кнопка в UI
  или `move --group-id N`).
* **Crash recovery**: транзакция БД коммитится после файловых операций. Если движок
  упал между ними, повторный `move` восстанавливает картину: файла нет в src, но он
  лежит в папке этой группы (нейминг 1.2.0+ выводится из имён членов группы) или в
  прежней `trash/group_{id}` → `moved_to` доносится. Recovery повторяет
  детерминированную аллокацию имён `_unique_target` (base, base_1, base_2…)
  и не переиспользует занятые слоты — одноимённые дубликаты не «приклеиваются»
  к одному файлу; проверка размера отсекает чужие файлы. Хэши всех перенесённых
  и восстановленных файлов удаляются, `moved_at` доносится. Хэши
  исчезнувших файлов удаляются, чтобы дубликаты не находились повторно.
* **Строки `files` перенесённых/исчезнувших файлов не удаляются, а помечаются
  `status='moved'`** — история групп и галерея остаются целыми; счётчики
  `status` учитывают помеченные строки отдельно, а вернувшийся на то же место
  файл переиндексируется обратно в `'ok'`. Миграция CHECK-ограничения
  идемпотентна (§5).

## 5. База данных (PostgreSQL)

Драйвер psycopg 3 (`psycopg[binary]`); в UI — `psycopg_pool.ConnectionPool`
(`st.cache_resource`, max 5, короткие запросы). DDL в `engine/db.py`, идемпотентный,
выполняется при старте движка (и командами `status`/`stop`).

| Таблица | Назначение |
|---|---|
| `files` | `path UNIQUE, size, mtime, width, height, indexed_at, status('ok'\|'corrupt'\|'moved'), error`. `'moved'` — файл перенесён в trash или исчез из src (история групп сохраняется; миграция CHECK-ограничения идемпотентна, выполняется при старте движка) |
| `hashes` | `(file_id, variant 0..7) PK, phash BYTEA, hash_part TEXT`, индекс по `hash_part` |
| `analysis_runs` | `created_at, threshold, params JSONB` — история прогонов |
| `groups` | `run_id, member_count, total_size, kept_path, confirmed, info JSONB` |
| `group_members` | `(group_id, file_id) PK, role('kept'\|'dup'), moved_to, moved_at` |
| `status` | singleton: `stage, processed, total, current_file, files_per_sec, started_at, updated_at, engine_pid, stop_requested, params JSONB` |
| `events` | `ts, level, message` — структурированный лог; движок пишет сюда и в stdout, старые записи подчищаются (последние ~1000). Никаких разделяемых лог-файлов между контейнерами |

DSN берётся из `PG_DSN` (по умолчанию `postgresql://photo:photo@db:5432/photo`).

## 6. UI на Streamlit (монитор и пульт)

Запрещено: обработка изображений (кроме ленивых миниатюр), обходы ФС, запросы без
LIMIT. Обязательно: частичные перерисовки через `st.fragment(run_every=...)`,
выборки с LIMIT/OFFSET или агрегатами, соединения только из пула. Точечные
исключения 1.4.0 (запуск движка из UI, возврат/удаление одного файла) — см. §1.

* **Баннер**: если `status.updated_at` устарел — «Движок не запущен»: подсказка
  командой `docker compose run --rm engine run` ИЛИ кнопками на «Мониторе».
  UI при этом полностью работоспособен для просмотра прошлых результатов.
* **Сайдбар**: пути (host-форма + проверка существования в контейнере); эффективные
  настройки + форма редактирования (пишет в settings.toml): paths (host-пути с
  валидацией корня до записи), threads/threshold/dry-run/move-mode/keep_by,
  три переключателя подтверждений; параметры последнего запуска движка
  (из `status.params`).
* **Монитор** (фрагмент): этап, прогресс-бар, «Обработано X из Y», текущий файл,
  скорость, ETA, счётчик битых файлов, сводка по последнему run. Управление:
  «🛑 Стоп» (флаг `stop_requested` — работает и для запусков из UI),
  «▶️ Запустить run» и «🔍 Запустить scan» (subprocess внутри web-контейнера;
  заблокированы, пока движок работает; лог запуска — в раскрывающемся блоке),
  «💥 Очистить все» (с диалогом или сразу — `ui.confirm_clean_all`): TRUNCATE
  результатов прогонов (индекс, хэши, группы, runs) и журнала; **файлы на диске
  не затрагиваются**; заблокирована при работающем движке. И «опасная зона»
  manual-режима — подтверждение переноса (с явным чекбоксом-предупреждением).
* **Журнал** (фрагмент): хвост `events` (последние 200) с автообновлением;
  кнопка «🧹 Очистить» — удаляет все записи (с диалогом или сразу —
  `ui.confirm_clean_log`).
* **Галерея**: пагинация по `page_size` групп (LIMIT/OFFSET); для группы — пути
  (host-форма), размеры; дубликаты помечены 📋; у ПЕРЕНЕСЁННЫХ дубликатов
  (файл лежит в trash) — кнопки:
  * «↩️ Вернуть» — файл перемещается из trash на прежнее место (`files.path`);
    если оно занято — рядом с суффиксом « (restored)»; перезапись запрещена.
    Хэши пересчитываются (на move они удалялись), `status` → 'ok', файл снова
    участвует в будущих run; событие пишется в журнал;
  * «🗑️ Удалить» — удаляет файл с диска (только внутри trash — защита от
    испорченной строки БД) и вычищает его строки из БД, уменьшая счётчики
    групп; перед удалением — диалог, если включён `ui.confirm_delete_files`.
  Кнопок у неперенесённых дубликатов нет — их обрабатывает этап move.
  Тумблер «Показать изображения»: оригинал и дубликаты рядом; миниатюры —
  дисковый кэш `/data/cache/thumbs` (имя = sha256 пути, ~400 px), ленивая
  генерация; `st.image` никогда не получает исходник без даунскейла. Кнопки
  подтверждения групп (manual) — здесь же.

## 7. Маунты, тома, права

| Маунт | engine | web | Зачем |
|---|---|---|---|
| `PHOTOS_ROOT → /photos` (единый, `.env`) | rw | rw | Хост-корень с `src/` и `trash/`. Движку rw — `shutil.move` между ФС = копия + удаление источника; web rw с 1.4.0 — «↩️ Вернуть»/«🗑️ Удалить» и запуск движка из UI. `bind.create_host_path: false` — при забытой папке compose сразу ошибётся явно |
| `./settings.toml` | `/app/settings.toml` **ro** | `/data/settings.toml` **rw** | Единый файл настроек (решение и EBUSY-фолбэк описаны в §3) |
| volume `pgdata` | — | — | Данные PostgreSQL |
| volume `thumbs` (`/data/cache`) | — | rw | Дисковый кэш миниатюр + лог запуска движка из UI |

Путь на хосте задаётся `PHOTOS_ROOT` в `.env` (см. `.env.example`) — например
`/home/me/myfotos`; тогда `PHOTOS_ROOT/src` и `PHOTOS_ROOT/trash` — рабочие
папки (имена — в `[paths]` settings.toml, редактируются из UI). Смена
`PHOTOS_ROOT` требует `docker compose up -d` (маунты нельзя менять на лету);
подпапки — меняются без рестарта.

Контейнер работает под non-root пользователем `appuser` (uid 1000). Bind-маунт
сохраняет права host-системы: создайте папки своим пользователем (`mkdir -p
photos/src photos/trash`), тогда запись будет разрешена. Если ваш uid ≠ 1000 —
`sudo chown -R 1000:1000 photos/trash` (или поправьте `useradd --uid` в Dockerfile).

`.dockerignore` исключает `src/`, `trash/`, `photos/`, `settings.toml`, `.env` из образа.

## 8. Измерение производительности UI (цель < 300 мс)

**Что измеряется**: полный реран скрипта Streamlit — wall-time от начала до конца
рендера, `time.perf_counter()`; в приложении это метрика **«UI rerun, мс»** в сайдбаре
(плюс avg(10) и max(30) по сессии). Автообновляемые вкладки работают как
`st.fragment` и реранятся **отдельно от страницы**, их локная длительность выводится
каптионом внутри фрагментов («фрагмент обновлён за N мс»).

**Как воспроизвести**:

1. `docker compose up -d db web`, открыть http://localhost:8501.
2. В соседнем терминале запустить движок на большом наборе:
   `docker compose run --rm engine run` (индексация на полной скорости).
3. Не закрывая терминал движка, в UI: подержать открытой вкладку «Монитор»
   (фрагменты тикают каждые `refresh_sec`), полистать страницы «Галереи»,
   попереключать вкладки — и снимать значения «UI rerun, мс».

**Зафиксированный критерий**: устойчиво **< 300 мс** при работающем движке.
Достигается: все запросы — LIMIT/агрегаты через пул (max 5), галерея — постранично,
миниатюры ленивые из дискового кэша, тяжёлые вкладки — фрагменты (перерисовывается
только вкладка). Если метрика превышает 300 мс — смотрите «Журнал» (нагрузка БД),
увеличьте `refresh_sec`, проверьте, что запросы не были заменены на неограниченные.

## 9. Приёмка (критерии и как проверить)

1. **Quickstart работает** — команды из §2 поднимают db+web и запускают движок.
2. **Повороты/отражения находятся** — `scripts/make_testset.py` создаёт оригиналы
   и копии (90/180/270, отражения, диагонали, resize+перекодирование); после
   `engine run` в галерее каждая копия попадает в группу к оригиналу (для пущей
   строгости: `engine run --dry-run` покажет план без переноса).
3. **kill -9 не портит БД, run продолжает** — во время scan:
   `docker ps --filter ancestor=photo-dedup:1.4.0 -q | xargs -r docker kill` (или
   `pkill -9 -f engine.cli` при локальном запуске), затем снова
   `docker compose run --rm engine run` — сканирование продолжится с места
   остановки (закоммиченные батчи пропускаются по `(path,size,mtime)`).
4. **UI отзывчив при индексации** — метрика «UI rerun, мс» < 300 при работающем
   движке (§8).
5. **auto-перенос создаёт папки групп с info.txt** — после `engine run` (mode=auto)
   в trash появляются папки, названные по оригиналу (`_IMG_…jpg`, при
   коллизиях `__2`), с `info.txt`; галерея показывает `moved_to`-пути (файлы
   читаются из trash), `group_members.moved_to` заполнено.
6. **Кнопки UI 1.4.0** — на «Мониторе»: «▶️ Запустить run» поднимает полный цикл
   (прогресс и журнал обновляются как у CLI-запуска, «🛑 Стоп» его останавливает);
   «💥 Очистить все» с диалогом опустошает БД, но файлы в src/trash остаются на
   месте. В галерее у перенесённого дубликата: «↩️ Вернуть» возвращает файл на
   прежнее место (файл исчезает из trash, хэши в БД восстановлены), «🗑️ Удалить»
   после диалога удаляет его с диска и из БД.

## 10. Известные ограничения

* Бакетный префикс 16 бит (по умолчанию): пары, различающиеся в первых 16 битах
  хэша, не сопоставляются (осознанный trade-off скорости, §4). Байт-в-байт
  копии при этом НЕ теряются никогда: у идентичных файлов совпадает весь phash,
  поэтому они всегда попадают в один бакет и находятся при любом threshold
  (дополнительно верифицируются sha256 на этапе move).
* phash — перцептивный хэш: близкие по смыслу кадры (серии съёмки) могут попадать
  в группы; регулируется `threshold` (0–4 консервативно, выше — агрессивнее).
  Точные копии внутри группы (равенство sha256 с оригиналом) помечаются
  автоматически — см. §4, этап move.
* Векторизованное сравнение в analyze требует хэшей ≤ 64 бит (hash_size ≤ 8);
  при больших — автоматический резерв на чистом Python (медленнее).
* HEIC/HEIF — опционально: раскомментируйте `pillow-heif` в `requirements.txt`
  и пересоберите образ.
* `refresh_sec` применяется после перезапуска web-контейнера (фрагменты создаются
  на старте процесса); остальные настройки UI — сразу, движка — на границе этапов.
* Движок, запущенный кнопкой из UI, — дочерний процесс web-контейнера: он умирает
  вместе с контейнером web и делит с ним ресурсы; приоритетный путь для длинных
  прогонов — по-прежнему `docker compose run --rm engine run`. Запуск из UI —
  для повседневных операций: статус/журнал/стоп работают одинаково.
* Смена `PHOTOS_ROOT` (.env) требует пересоздания контейнеров (`docker compose
  up -d`) — маунты docker нельзя менять на лету; подпапки src/trash — без рестарта.

## 12. Изменения в 1.4.0 (доработки по запросу пользователя)

* **Пути на хосте + редактирование из UI.** `[paths]` в settings.toml и в
  UI теперь хранит пути КАК НА ХОСТЕ (`/home/me/myfotos/src`) и правится из
  формы настроек. Хост-корень задаётся один раз (`PHOTOS_ROOT` в .env,
  единый rw-маунт `→ /photos` в обоих контейнерах), внутри контейнеров пути
  прозрачно переводятся префиксом (`PATH_MAP_HOST`/`PATH_MAP_CONTAINER`):
  маунты docker нельзя менять на лету, а подпапки внутри корня — можно, без
  рестарта. Путь вне корня — внятная ошибка валидации (в UI до записи и при
  старте движка), а не молчаливое сканирование пустой папки.
* **БАГФИКС: сохранение настроек из UI падало** «[Errno 16] Device or resource
  busy: '/data/.settings.toml.tmp-N' → '/data/settings.toml'»: при файловом
  bind-mount settings.toml подмена inode (`os.replace`) поверх mountpoint
  невозможна. Запись теперь выполняется НА МЕСТО в тот же inode с fsync —
  ошибок нет, все контейнеры видят обновление; атомарный путь `os.replace`
  сохранён для обычных (не файловых) маунтов.
* **Галерея: «↩️ Вернуть» и «🗑️ Удалить»** у перенесённых дубликатов (файл
  в trash): возврат на прежнее место с пересчётом хэшей и `status='ok'`
  (коллизия имени — суффикс « (restored)», перезапись запрещена); удаление
  с диска и из БД (только внутри trash — защита от испорченной строки),
  счётчики групп корректируются; обе операции пишут события в журнал
  (префикс `web:`). Иконка дубликата в списке: 🗑 → **📋**. Новый параметр
  `ui.confirm_delete_files` (диалог удаления; правится из UI).
  Логика — в новом модуле `web/actions.py` (без streamlit, покрыт тестами).
* **Монитор: запуск движка из UI.** Кнопки «▶️ Запустить run» и
  «🔍 Запустить scan» стартуют `python -m engine.cli run|scan` как subprocess
  внутри web-контейнера (эквивалент `docker compose run --rm engine …` по
  эффекту: тот же образ/env/маунты; без проброса docker.sock в web). Двойной
  запуск заблокирован (по статусу в БД и по живым процессам), лог запуска —
  в раскрывающемся блоке, «🛑 Стоп» останавливает как обычные запуски.
* **Монитор: «💥 Очистить все».** `db.wipe_results`: одна транзакция TRUNCATE
  результатов прогонов (files → hashes/group_members, analysis_runs → groups)
  и журнала + сброс `status` в idle. ФАЙЛЫ НА ДИСКЕ не затрагиваются; в диалоге
  предупреждение именно про результаты и журнал; кнопка заблокирована при
  работающем движке. Новый параметр `ui.confirm_clean_all` (правится из UI).
* **Журнал: «🧹 Очистить»** — удаляет все записи events; новый параметр
  `ui.confirm_clean_log` (правится из UI). Внутри автообновляемых фрагментов
  подтверждение реализовано двухшаговой кнопкой (диалоги st.dialog внутри
  fragment ненадёжны); в галерее — настоящий st.dialog.
* Прочее: `status.params` показывает src/trash в host-форме; в compose добавлен
  `.env.example`; тесты: smoke 1i–1k (confirm-дефолты, PATH_MAP, EBUSY-фолбэк),
  integ 14–16 (restore/delete/wipe на реальной БД).

## 13. Изменения в 1.3.0 (P2-хвост)

* **UI: атомарная запись settings.toml.** Форма в сайдбаре пишет через временный
  файл в том же каталоге + fsync + `os.replace` — устранена и гонка с
  `reload_settings` движка на границе этапов (движок всегда читает целостный
  файл), и риск пустого/оборванного файла при сбое записи.
* **UI: галерея без N+1.** Члены всех групп страницы выбираются ОДНИМ батч-запросом
  (`WHERE gm.group_id = ANY(...)`, ограничен page_size групп) вместо запроса на
  каждую группу.
* **Статус: честные единицы скорости.** На этапе analyze скорость — «бакетов/с»
  (это и есть натуральная единица этапа), на scan/move — «файлов/с» (CLI `status`
  и монитор UI). ETA считается в тех же единицах, т.е. остаётся корректным.
* **БД: строки перенесённых/исчезнувших файлов помечаются `status='moved'`**
  (раньше они оставались «мёртвыми» строками со статусом `'ok'`). История групп
  и галерея сохраняются; счётчики в `engine status` показывают
  «перенесено/отсутствует» отдельно; вернувшийся на то же место файл
  переиндексируется обратно в `'ok'`.
  Миграция CHECK-ограничения идемпотентна и выполняется при каждом старте движка
  (старые БД поднимаются автоматически).
* **move: детерминированный crash-recovery при одноимённых дубликатах.** Раньше
  два дубликата с одинаковым именем в одной группе могли «приклеиться» к одному
  и тому же файлу в trash (второй оставался неучтённым). Теперь recovery
  повторяет аллокацию имён `_unique_target` (base, base_1, base_2…) в порядке
  членов группы и не переиспользует занятые слоты; хэши восстановленных
  файлов тоже удаляются, `moved_at` доносится.
* **scan: подсчёт файлов-кандидатов в фоновом потоке** — устранён отдельный
  блокирующий обход дерева до хэширования (двойной обход); знаменатель
  прогресс-бара подтягивается, как только счёт готов.
* Тесты: smoke 1h (атомарная запись), integ §10 (батч-запрос членов страницы),
  §13 (recovery одноимённых дубликатов, `files.status='moved'`, moved_at/хэши).

## 14. Изменения в 1.2.0

* **move: новая политика оригинала `keep_by=capture` (новый дефолт).** Оригинал
  определяется по времени снимка: json-Takeout-sidecar (`photoTakenTime` →
  `creationTime`) → файловая система (`min(birthtime, mtime)`, на Windows —
  `st_ctime`) → тай-брейк по «копийным» маркерам имени (`(Copy 2)`, `(1)`,
  ` — копия`, `-edited` проигрывают чистому имени) → путь. Решает кейс, когда
  `IMG_20260912_163920.jpg` шёл после своих `(Copy N)` по сортировке и
  считался дубликатом. Старые политики `size`/`pixels` доступны как и раньше
  (CLI `--keep-by`, settings.toml, UI).
* **move: папки групп называются по оригиналу** (`_IMG_20260914_123649.jpg`
  вместо `group_N`, префикс настраивается `move.group_name_prefix`).
  Санитизация под Windows/macOS/Linux, уникальность без учёта регистра (NFC),
  коллизии между группами — `__2`, `__3`. Имя папки пишется в `groups.info`
  (`group_dir`); в `info.txt` добавлены время снимка оригинала и его источник.
* **analyze/move**: в подсказку kept на analyze добавлен mtime из БД;
  crash-recovery ищет перенесённые файлы и в именованных папках групп,
  и в прежних `group_{id}` (с проверкой размера).
* Тесты: smoke §6 (парсер Takeout-времён, name-penalty, capture-выбор,
  санитизация/коллизии имён), integ §12 (json-sidecar vs ФС, чистое имя против
  `(Copy N)`, коллизии папок групп), обновлены интеграционные проверки нейминга.

## 15. Изменения в 1.1.0

* **analyze: устойчивость и память.** Попарное сравнение в бакете переведено на
  2D-блоки — пик памяти ограничен десятками МБ независимо от размера бакета
  (раньше блок 2048×n на «плоском» бакете из 30 тыс. похожих кадров расходовал
  ~1,3 ГБ). Хэши разной длины (смена `hash_size` без `--force`) больше не роняют
  analyze с `OverflowError`: бакет делится на подгруппы равной длины.
* **move: dry-run полностью read-only.** Раньше при отсутствующих файлах группы
  dry-run изменял БД (удалял хэши, писал `groups.info`) — теперь в dry-run не
  выполняется ни одной записи: действия только планируются в events.
* **move: точная верификация копий по sha256.** Дубликаты каждой группы
  хэшируются sha256; равные оригиналу помечаются в dry-run-плане, в `info.txt`
  и в `groups.info` (`exact_kept_copies`, `dups_sha_checked`). Байт-в-байт копии
  гарантированно находятся при любом threshold (совпадение полного phash).
* Тесты: smoke 2e/3e/3f (sha256, 2D-чанкинг, смешанные длины), integ 11a/11b
  (dry-run read-only, sha256-верификация).
