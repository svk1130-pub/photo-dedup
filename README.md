# Photo Dedup — движок поиска дубликатов + тонкий Streamlit-UI

Готовое Python-приложение для поиска и перемещения **изменённых / повёрнутых / зеркальных**
дубликатов фотографий в больших архивах (до 3 ТБ, сотни тысяч файлов, вложенные подпапки).

Приоритет проекта — **прототип для теста Streamlit как фронтенда к долго работающему
высоконагруженному бэкенду**: вся тяжёлая логика живёт в отдельном CLI-процессе,
Streamlit — тонкий клиент, который только читает состояние из PostgreSQL и пишет
команды-флаги. UI остаётся отзывчивым при полной загрузке движка (ориентир —
реран UI < 300 мс, см. раздел «Измерение производительности»).

Основной сценарий: движок запускается из командной строки
(`docker compose run --rm engine run` или `python -m engine.cli run`), веб-интерфейс
открывается опционально — для мониторинга и управления. Движок корректно работает
при полностью закрытом UI.

---

## 1. Архитектура

Четыре независимых процесса (контейнера), общаются только через PostgreSQL:

```
┌─────────────────┐        ┌──────────────────────┐        ┌─────────────────┐
│  engine (CLI)   │        │  PostgreSQL 16 (db)  │        │  web (Streamlit)│
│  scan/analyze/  │──W──▶  │  files, hashes,      │  ◀──R──│  :8501, тонкий  │
│  move/run/stop  │──W──▶  │  groups, status,     │  ──W─▶ │  клиент, пул ≤5 │
│  ThreadPool×N   │        │  events, runs, jobs  │        │  флаги/настройки│
└─────────────────┘        └──────────┬───────────┘        └─────────────────┘
      ▲                               │ LISTEN/NOTIFY          thumbs volume
      │ CLI: docker compose           ▼                        pgdata volume
      │ run --rm engine …    ┌──────────────────────┐
      │ (человек, без        │  runner (1.5)        │
      │ автозапуска)         │  вечный цикл: берёт задание из jobs (SKIP LOCKED) │
      └──────────────────────│  и выполняет код движка in-process, без сокета │
                             └──────────────────────┘
```

* **db** — `postgres:16-alpine`, healthcheck `pg_isready`, named volume `pgdata`.
* **engine** — CLI (`python:3.12-slim`, non-root). Не автозапускается, не рестартует:
  используется только через `docker compose run --rm engine <команда>`
  (`run`/`scan`/`analyze`/`move`/**`undo`**/**`clean-db`**/`status`/`stop`).
* **runner** (1.5.0 Ф1 + 1.6.0 Ф2) — исполнитель очереди `jobs`: тот же образ/маунты/env,
  что у engine, вечный цикл (`restart: unless-stopped`), атомарно берёт задание
  (`FOR UPDATE SKIP LOCKED` + guard «движок уже работает?») и выполняет его
  **in-process** — тот же код, что и CLI, без subprocess; пробуждение —
  LISTEN/NOTIFY, живость — heartbeat, зависшие задания — stale на рестарте.
  Docker-сокет не нужен.
* **web** — Streamlit `:8501`, наружу — **порт хоста 9501** (`http://localhost:9501`),
  `--server.headless=true`, healthcheck `/_stcore/health`, `restart: unless-stopped`.
  **Никогда** не запускает процессы — читает БД, пишет флаги
  (`stop_requested`, `groups.confirmed`) и настройки, ставит задания в очередь
  `jobs`; точечные файловые операции
  (⭐/📋/↩️/🗑️/undo) выполняет через `engine/webops.py` и блокирует их,
  пока движок работает.

UI умеет шесть вещей помимо чтения: кнопка «Стоп» (флаг `stop_requested`),
подтверждение групп для переноса в manual-режиме (`groups.confirmed`), запись
настроек в `settings.toml`, ручные файловые операции галереи (⭐ «Это оригинал» /
📋 «Это дубликат» / ↩️ Вернуть / 🗑️ Удалить / ℹ️ Свойства), обслуживание БД
(«💥 Очистить БД», «↩️ Отменить всё», «🧹 Очистить журнал») и запуск прогона
через очередь (кнопки ▶️/🔍/🧠/📦/↩️ на Мониторе — INSERT в `jobs`, выполняет
сервис `runner`). Всё остальное — только SELECT с LIMIT/агрегатами.

## 2. Quickstart

Требуется Docker Compose v2.20+ (используется `bind.create_host_path`).

```bash
cd photo-dedup

# 1. Настройки, хост-корень фото и рабочие каталоги (создайте их СВОИМ
#    пользователем, см. §7 про права)
cp settings.example.toml settings.toml
cp .env.example .env            # PHOTOS_ROOT=./ — фото рядом с проектом;
                                # укажите свой корень, напр. PHOTOS_ROOT=/data/foto_test
mkdir -p src trash
# положите фотографии в $PHOTOS_ROOT/src (для быстрого теста можно сгенерировать набор, см. ниже)

# 2. Сборка и запуск БД + UI + runner (исполнитель очереди заданий)
docker compose build
docker compose up -d db web runner
# UI: http://localhost:9501   (8501 часто занят — поэтому 9501)

# 3. Тестовый набор с поворотами/отражениями (критерий приёмки №2):
docker compose run --rm --entrypoint python engine scripts/make_testset.py /data/src/testset 5

# 4. Полный цикл: scan → analyze → move (с Resume)
docker compose run --rm engine run     # или кнопка «▶️ Полный прогон» в UI

# 5. Статус / мягкая остановка / возобновление
docker compose run --rm engine status
docker compose run --rm engine stop
docker compose run --rm engine run          # продолжит с места остановки

# 6. Остановить фоновые сервисы (данные в volume pgdata сохранятся)
docker compose down
```

Примечание о `stop`: флаг действует на **работающий** движок — он доделает текущий
файл/батч и остановится. При старте следующей рабочей команды флаг сбрасывается,
поэтому устаревший флаг не помешает будущим запускам.

Движок можно запускать и при закрытом UI, и поэтапно:

```bash
docker compose run --rm engine scan                     # только индексация
docker compose run --rm engine analyze                  # только поиск групп
docker compose run --rm engine move --dry-run           # план переноса
docker compose run --rm engine move                     # перенос (auto-режим)
docker compose run --rm engine move --move-mode manual  # только подтверждённые группы
docker compose run --rm engine run --dry-run --threads 4 --threshold 6
docker compose run --rm engine undo --dry-run           # план отмены переносов
docker compose run --rm engine undo                     # вернуть ВСЁ из trash + очистить БД
docker compose run --rm engine clean-db                 # очистить результаты и журнал

# Отложенный запуск (очередь jobs, выполнит runner; 1.9.0)
docker compose run --rm engine schedule run --delay 90m            # полный прогон через 90 минут
docker compose run --rm engine schedule run --at "21:30"           # сегодня в 21:30 (если ещё не прошло)
docker compose run --rm engine schedule move --at "2026-10-10 09:00" --dry-run
```

Флаги CLI **имеют приоритет** над settings.toml: `--threads`, `--threshold`,
`--dry-run`, `--move-mode`, `--keep-by`, `--force`, `--group-id`, `--settings`.

Отложенный запуск из CLI (1.9.0): `engine schedule JOB --at MOMENT | --delay
DELAY` — ставит задание в очередь с отсрочкой (JOB: run/scan/analyze/move/undo;
ровно один из `--at`/`--delay`, форматы и валидация — §12); выполняет сервис
runner, перенос/отмена — блок «Очередь runner» в UI.

Локально без docker (нужны Python 3.12, PostgreSQL и `pip install -r requirements.txt`):

```bash
export PG_DSN=postgresql://photo:photo@localhost:5432/photo
export SETTINGS_PATH=./settings.toml
python -m engine.cli run
PYTHONPATH=. streamlit run web/app.py --server.headless=true
```

## 3. Настройки (settings.toml)

Читается стандартным `tomllib`, пишется `tomli-w`. Приоритет: **CLI-флаги >
settings.toml > дефолты**. Поставляется `settings.example.toml` с комментариями.

| Секция | Ключ | Дефолт | Смысл / когда применяется |
|---|---|---|---|
| `[paths]` | `src`, `trash` | `/data/src`, `/data/trash` | **Контейнерные** пути (их видит движок; не зависят от места архива). На хосте им соответствует `PHOTOS_ROOT` из `.env`. Валидация при старте: `trash` внутри `src` (или совпадение) → аварийный выход с понятной ошибкой |
| `[scan]` | `extensions` | `.jpg .jpeg .png .webp .bmp .tiff` | Какие файлы индексировать |
| `[scan]` | `recursive` | `true` | Обходить подпапки |
| `[scan]` | `threads` | `8` | Потоки хэширования. Применится на этапе **scan** |
| `[scan]` | `batch_size` | `200` | Размер батча записи в БД (одна транзакция) |
| `[scan]` | `read_exif` | `true` | Читать EXIF-свойства при прогоне → `files.exif` (окно «ℹ️ Свойства» в галерее). `false` — свойства читаются лениво из UI при открытии окна |
| `[hash]` | `method` | `phash` | `imagehash.phash` |
| `[hash]` | `hash_size` | `8` | 64-битный хэш |
| `[hash]` | `hash_part_len` | `4` | Hex-символов на бакет (4 = 16 бит) |
| `[analyze]` | `threshold` | `4` | Макс. расстояние Хэмминга. Применится на этапе **analyze** |
| `[move]` | `mode` | `auto` | `auto` — все группы; `manual` — только `confirmed`. Применится на этапе **move** |
| `[move]` | `keep_by` | `capture` | Что считать оригиналом: `capture` — по времени снимка (см. §4), `size` (макс. размер), `pixels` (макс. разрешение) |
| `[move]` | `group_name_prefix` | `_` | Префикс имён папок групп в trash: `_IMG_20260914_123649.jpg` (имя строится по файлу-оригиналу; `""` — без префикса) |
| `[move]` | `conflict` | `suffix` | Коллизии имён файлов внутри папки группы: `_1`, `_2`…; коллизии имён самих папок групп — `__2`, `__3`… |
| `[move]` | `dry_run` | `false` | Dry Run главнее переноса: физически ничего не перемещается |
| `[ui]` | `page_size` | `15` | Групп на страницу галереи (применяется сразу) |
| `[ui]` | `refresh_sec` | `2` | Автообновление фрагментов (применяется после рестарта web) |
| `[ui]` | `confirm_delete_files` | `true` | Диалог подтверждения при «🗑️ Удалить» в галерее |
| `[ui]` | `confirm_clean_db` | `true` | Диалог подтверждения при «💥 Очистить БД» (монитор) |
| `[ui]` | `confirm_clean_log` | `true` | Диалог подтверждения при «🧹 Очистить журнал» |

**Где лежат фото на хосте — одна переменная `.env`: `PHOTOS_ROOT`.** Маунты
compose строятся из неё: `${PHOTOS_ROOT}/src → /data/src`, `${PHOTOS_ROOT}/trash →
/data/trash` (по умолчанию `./` — папки рядом с compose-файлом). Поэтому
`[paths]` в settings.toml не нужно трогать при переносе архива, а UI-сайдбар
показывает соответствие «контейнер → хост» (`engine/settings.py:
container_to_host`). Смена хост-папки: правка `.env` + `docker compose up -d`.
Правка `[paths]` из UI маунты не меняет принципиально — поэтому пути в форме
редактора не редактируются, а показываются с этой подсказкой.

Движок **перечитывает настройки на границе этапов** (`run`: scan → analyze → move),
UI показывает эффективную конфигурацию и помечает в подсказках полей, когда
каждое изменение применится. Ошибки в файле — внятное сообщение с номером строки
(синтаксис) или ключом секции (типы), не трейсбек.

**Как UI пишет настройки (выбор маунта).** `settings.toml` — один host-файл,
примонтированный в оба контейнера:

* engine: `./settings.toml → /app/settings.toml` с флагом **`:ro`** — движок настройки
  только читает, случайно повредить файл он не может;
* web: тот же `./settings.toml → /data/settings.toml` **без `:ro`** — форма в сайдбаре
  пишет именно в него (читаем TOML → мерджим → пишем tomli-w).

Это даёт единственный источник правды: правки из UI мгновенно видны CLI-движку
на следующем этапе/запуске, ручные правки — видны UI. Нюансы: (а) при сохранении
из UI комментарии TOML теряются (ограничение tomli-w), а сама запись атомарна
(временный файл в том же каталоге + fsync + os.replace — движок, перечитывающий
настройки на границе этапов, всегда видит целостный файл, без разрыва на границе
записи); (б) **если `settings.toml` примонтирован одиночным файлом**, `os.replace`
поверх точки маунта невозможен (EBUSY, «Device or resource busy», Errno 16) —
запись автоматически откатывается на запись на месте (открыть/усечь/записать/fsync),
ошибка сохранения исключена при любом способе маунта; (в) в compose включён `bind.create_host_path: false`,
поэтому если забыть `cp settings.example.toml settings.toml`, compose сразу
выведет понятную ошибку вместо тихого создания каталога.

## 4. Как работает движок

### Этап 1 — scan (индексация)

* Рекурсивный `os.walk` с учётом `recursive`; пропускаются папка `trash`, скрытые
  директории и симлинки (защита от циклов).
* Общее число файлов-кандидатов (знаменатель прогресс-бара) считается в
  фоновом потоке параллельно с хэшированием — двойной обход дерева устранён;
  как только счёт готов, прогресс-бар и ETA появляются в статусе/UI.
* `ThreadPoolExecutor(threads)`: воркеры **только вычисляют хэши**, все записи в БД
  делает главный поток пачками `executemany` (batch_size) в одной транзакции —
  нет конкурентной записи, статус обновляется раз в батч.
* Для JPEG — `img.draft("RGB", (512, 512))` до декодирования (многократное ускорение);
  затем `ImageOps.exif_transpose` (Pillow сам EXIF-поворот не применяет).
* **EXIF-свойства** (`scan.read_exif`, дефолт true): на этапе scan читаются
  заголовки APP1 (без декодирования пикселей) и складываются в `files.exif JSONB`
  — камера, выдержка, диафрагма, ISO, вспышка, замер, фокусное, дата съёмки;
  их показывает окно «ℹ️ Свойства» в галерее. `false` — свойства читаются
  лениво из UI при первом открытии окна и кэшируются в БД.
* **Инвариантность к D4**: для каждого файла считаются 8 phash — по всем элементам
  группы D4: identity (исходное изображение — в `PIL.Image.Transpose` ровно 7 режимов,
  единичный элемент это картинка без трансформации), ROTATE_90/180/270,
  FLIP_LEFT_RIGHT, FLIP_TOP_BOTTOM, TRANSPOSE, TRANSVERSE. Никакой min-канонизации:
  композиция поворота и отражения не входит в набор из 5, зеркальные копии терялись
  бы. Все 8 вариантов — отдельными строками в `hashes`.
* **Resume**: файл пропускается, если в БД есть запись с тем же `(path, size, mtime)`
  и хэши на месте (учёт и ранее «битых» файлов — они не ретраятся каждый запуск).
  Изменившийся файл переиндексируется: сначала удаляются его старые строки хэшей.
  Принудительная переиндексация — `--force`.
* Битые файлы (в т.ч. `DecompressionBombError`, `UnidentifiedImageError`) получают
  `status='corrupt'` с текстом ошибки в `files.error`.
* **Остановка**: флаг `stop_requested` проверяется перед постановкой каждого файла;
  текущие in-flight файлы доделываются, батч коммитится, статус → `stopped`.
  SIGINT/SIGTERM обрабатываются так же (первый сигнал — мягкая остановка, второй —
  принудительный выход): `docker stop` и Ctrl+C не портят данные.

### Этап 2 — analyze (поиск групп)

* Бакеты по `hash_part` перебираются **потоковым серверным курсором**
  (`cursor(name=...)`, `itersize`) — один проход по `hashes`, ничего не тащится в RAM.
* Внутри бакета — попарное расстояние Хэмминга по полному phash (XOR + popcount;
  для 64-битных хэшей векторизовано numpy: `np.bitwise_count`). Пары считаются
  **2D-блоками** (строки × столбцы): память ограничена блоком ~1024×1024
  (десятки МБ) независимо от размера бакета — даже «плоский» бакет из десятков
  тысяч похожих кадров не приводит к OOM. Кандидат — ЛЮБАЯ пара вариантов
  (файл A, вариант i) ↔ (файл B, вариант j) с дистанцией ≤ threshold.
* **Смешанная длина хэшей** (после смены `hash_size` без `--force` старые
  8-байтные строки соседствуют с новыми): несравнимые хэши делятся на
  подгруппы равной длины и обрабатываются независимо — смешанный бакет не
  роняет analyze.
* Группы — транзитивное замыкание через **union-find** внутри бакета
  (A~B, B~C ⇒ одна группа, даже если A!~C).
* Результаты персистятся: `analysis_runs` + `groups`/`group_members`. Галерея всегда
  читает последний `run_id`; старые прогоны остаются в истории. Повторный анализ
  создаёт новый run, старые не трогает. Незавершённый (остановленный) run удаляется.
* **Документированный trade-off**: пары, чьи хэши различаются в первых 16 битах
  (hash_part_len=4 hex), не попадут в один бакет и не будут найдены — это осознанная
  плата за O(сумма квадратов размеров бакетов) вместо O(n²) по всему архиву.
* В `groups.info` сохраняются `min_distance` (мин. дистанция в группе), `kept_by`,
  threshold; `groups.kept_path` — предварительный оригинал по текущему `keep_by`.

### Этап 3 — move (перенос)

* Режим из настроек (`mode: auto|manual`), переопределяется `--move-mode` и
  переключателем в UI. **Dry Run всегда главнее**: фиксируется только план (events),
  физически ничего не переносится, **БД не меняется** — в том числе не
  восстанавливаются `moved_to` и не удаляются хэши отсутствующих файлов
  (эти действия попадают в план, как и перенос).
* **Точная верификация sha256**: перед переносом дубликаты группы хэшируются
  `sha256` (только чтение — допустимо и в dry-run). Равенство хэша оригинала —
  байт-в-байт копия независимо от phash и порога Хэмминга. В dry-run план
  помечает точные копии («· точная копия оригинала (sha256)»); после переноса
  счётчик пишется в `info.txt` и `groups.info` (`exact_kept_copies`,
  `dups_sha_checked`).
* «Оригинал» выбирается по текущему `keep_by`:
  * **`capture` (дефолт)** — по времени снимка. Иерархия источников для каждого
    файла (первый успешный выигрывает): ① Google-Takeout-sidecar `<файл>.json`
    рядом с файлом — `photoTakenTime` → `creationTime` (парсится только
    `timestamp`, локализованное `formatted` игнорируется; мусор/будущее —
    отбрасывается); ② файловая система — `min(birthtime, mtime)`: копии
    наследуют mtime источника, но получают новый birthtime, поэтому минимум
    двух времён ≈ время появления контента (на Windows роль birthtime играет
    `st_ctime`; если ФС не хранит birthtime — остаётся mtime); ③ mtime из БД.
    Тай-брейки при равном времени: «копийные» маркеры имени (` (Copy 2)`,
    ` (1)`, ` — копия`, `-edited`…) проигрывают чистому имени, затем —
    **ранний ctime** (кейс «скопировали и переименовали в короткое `2.jpg`»:
    копия наследует mtime источника — время снимка выходит равным, — но её
    ctime = момент копирования, позже, чем у оригинала; раньше такой тай
    решался лексикографикой пути и короткое имя выигрывало ошибочно),
    далее — лексикографический путь. На этапе analyze роль kept — подсказка по mtime
    из БД; финальный выбор делается на move, когда доступна файловая система.
  * `size` — максимальный размер; `pixels` — максимальное разрешение.
* **Папка группы называется по оригиналу**: `_IMG_20260914_123649.jpg`
  (префикс настраивается `move.group_name_prefix`; прежний нейминг
  `group_{id}` остаётся fallback-ом для пустых имён). Риски нейминга закрыты:
  коллизии между группами — суффикс `__2`, `__3` (сравнение без учёта
  регистра, NFC — на macOS/Windows `IMG.jpg` и `img.jpg` одно имя);
  запрещённые для Windows символы (`< > : " / \ | ? *`, управляющие) и
  зарезервированные имена (CON, NUL, COM1…) санитизируются; хвостовые
  точки/пробелы срезаются; стем длиннее 100 символов обрезается. Папки,
  созданные прежними прогонами (в т.ч. старые `group_N`), учитываются и не
  переименовываются.
* Перенос через `shutil.move` (src и trash могут быть на разных ФС);
  коллизии имён файлов внутри папки группы — суффикс `_1`, `_2`…; рядом
  пишется `info.txt`: исходные пути, размеры, что оставлено, критерий
  оригинала, время снимка и его источник (для capture), порог, дата.
* После переноса обновляются `group_members.moved_to/moved_at` и `groups.kept_path` —
  галерея показывает новое расположение, а не мёртвые пути.
* В manual-режиме переносятся только группы с `confirmed = true` (кнопка в UI
  или `move --group-id N`).
* **Crash recovery**: транзакция БД коммитится после файловых операций. Если движок
  упал между ними, повторный `move` восстанавливает картину: файла нет в src, но он
  лежит в папке этой группы (нейминг 1.2.0+ выводится из имён членов группы) или в
  прежней `trash/group_{id}` → `moved_to` доносится. Recovery повторяет
  детерминированную аллокацию имён `_unique_target` (base, base_1, base_2…)
  и не переиспользует занятые слоты — одноимённые дубликаты не «приклеиваются»
  к одному файлу; проверка размера отсекает чужие файлы. Хэши всех перенесённых
  и восстановленных файлов удаляются, `moved_at` доносится. Хэши
  исчезнувших файлов удаляются, чтобы дубликаты не находились повторно.
* **Строки `files` перенесённых/исчезнувших файлов не удаляются, а помечаются
  `status='moved'`** — история групп и галерея остаются целыми; счётчики
  `status` учитывают помеченные строки отдельно, а вернувшийся на то же место
  файл переиндексируется обратно в `'ok'`. Миграция CHECK-ограничения
  идемпотентна (§5).

### Этап 4 — ручные операции и обслуживание (`engine/webops.py`)

Единая реализация операций, доступных и из UI, и из CLI. Все они согласованы
с инвариантами move-этапа (файловые операции ДО транзакции), журналируются
в `events` и БЛОКИРОВАНЫ, пока движок работает (guard `engine_running`):

| Операция | Что делает |
|---|---|
| `return_file` (↩️) | Вернуть перенесённый файл из trash на исходное место (`moved_to=NULL`, `status='ok'`; занятый исходный путь → суффикс `_restored`). Роль остаётся «дубликат»: следующий move перенесёт снова, ⭐ назначит оригиналом |
| `star_as_original` (⭐) | Обмен ролями: файл возвращается в src, текущий оригинал переносится в папку группы, `groups.kept_path` обновляется |
| `mark_as_duplicate` (📋) | Перенести файл в trash; если это был оригинал — новый выбирается автоматически по `keep_by` |
| `delete_file` (🗑️) | Удалить файл с диска + вычистить строки из БД (каскад), пересчитать счётчики группы |
| `undo_all` (`engine undo`) | Вернуть ВСЕ перенесённые файлы, удалить пустые папки групп; при успехе — TRUNCATE результатов и журнала; при проблемах — очистка откладывается, повторный undo пропускает уже возвращённое |
| `clean_db` (`engine clean-db`) | TRUNCATE результатов и журнала; файлы на диске не трогаются |

После файловых операций info.txt папки группы переписывается под фактическое
состояние (или пустая папка удаляется) — crash-recovery не ломается. Вернувшиеся
файлы имеют `status='ok'`, но без хэшей — следующий scan переиндексирует их
сам (resume видит «ok без хэшей»).

Подробная механика с фрагментами кода — `docs/LOGIC_EXT.md` §5–6.

## 5. База данных (PostgreSQL)

Драйвер psycopg 3 (`psycopg[binary]`); в UI — `psycopg_pool.ConnectionPool`
(`st.cache_resource`, max 5, короткие запросы). DDL в `engine/db.py`, идемпотентный,
выполняется при старте движка (и командами `status`/`stop`).

| Таблица | Назначение |
|---|---|
| `files` | `path UNIQUE, size, mtime, width, height, indexed_at, status('ok'\|'corrupt'\|'moved'), error, exif JSONB`. `'moved'` — файл перенесён в trash или исчез из src (история групп сохраняется; миграции CHECK и `exif` идемпотентны, выполняются при старте движка) |
| `hashes` | `(file_id, variant 0..7) PK, phash BYTEA, hash_part TEXT`, индекс по `hash_part` |
| `analysis_runs` | `created_at, threshold, params JSONB` — история прогонов |
| `groups` | `run_id, member_count, total_size, kept_path, confirmed, info JSONB` |
| `group_members` | `(group_id, file_id) PK, role('kept'\|'dup'), moved_to, moved_at` |
| `status` | singleton: `stage, processed, total, current_file, files_per_sec, started_at, updated_at, engine_pid, stop_requested, params JSONB` |
| `events` | `ts, level, message` — структурированный лог; движок пишет сюда и в stdout, старые записи подчищаются (последние ~1000). Никаких разделяемых лог-файлов между контейнерами |

DSN берётся из `PG_DSN` (по умолчанию `postgresql://photo:photo@db:5432/photo`).

## 6. UI на Streamlit (тонкий монитор и пульт)

Запрещено: обработка изображений (кроме ленивых миниатюр), обходы ФС, запросы без
LIMIT; исключение — точечные файловые операции `engine/webops.py` по путям из БД,
заблокированные на время работы движка. Обязательно: частичные перерисовки через
`st.fragment(run_every=...)`, выборки с LIMIT/OFFSET или агрегатами, соединения
только из пула.

* **Баннер**: если `status.updated_at` устарел — «Движок не запущен…» с
  подсказкой запустить кнопкой «▶️ Полный прогон» (Монитор) или командой
  `docker compose run --rm engine run`. UI при этом полностью работоспособен
  для просмотра прошлых результатов.
* **Свежая БД (таблиц ещё нет)**: вместо вводящего в заблуждение «PostgreSQL
  недоступен» UI показывает предупреждение с командой первичной инициализации
  `docker compose run --rm engine status` — схему создаёт движок при первом
  запуске (1.4.2).
* **Сайдбар**: пути (контейнерные + соответствие на хосте через `PHOTOS_ROOT`);
  эффективные настройки + форма редактирования (пишет в settings.toml): поля
  threads/read_exif/threshold/dry-run/move-mode/keep_by/page_size/refresh_sec
  и флаги подтверждений `ui.confirm_*` — с пометками, когда применятся;
  параметры последнего запуска движка (из `status.params`).
* **Монитор** (фрагмент): этап, прогресс-бар, «Обработано X из Y», текущий файл,
  скорость, ETA, счётчик битых файлов, сводка по последнему run.
  Кнопка «Стоп» (пишет `stop_requested`); **кнопки запуска (1.5.0 Ф1 + 1.6.0 Ф2)** —
  «▶️ Полный прогон», «🔍 Скан», «🧠 Анализ», «📦 Перенос», «↩️ Undo» (с
  подтверждением) — ставят задания в очередь `jobs` (выполняет сервис `runner`)
  и блок очереди: «⏳ в очереди» / «🏃 runner выполняет #id» + история последних 5
  заданий (state, exit code, длительность, ошибка) + предупреждение
  «⚠️ Прогон оборвался» при stale-заданиях (reap по протухшему heartbeat
  выполняется и из UI); **информер «что делать дальше»**
  (в manual-режиме показывает подтверждено X из Y и команду переноса); блок
  «⌨️ Быстрые команды» (копирование в один клик); «опасные зоны»:
  подтверждение переноса (manual, с чекбоксом-предупреждением) и обслуживание —
  **«💥 Очистить БД»** (TRUNCATE результатов+журнала, файлы не трогаются) и
  **«↩️ Отменить всё (undo)»** (возвращает все перенесённые файлы в src, затем
  чистит БД) — обе с подтверждением и с блокировкой при работающем движке.
  **Отложенный запуск (1.7.0 Ф3; выбор даты — 1.8.0)**: селект «Когда запускать»
  (Сейчас / через 30 мин / 1 ч / 3 ч / сегодня в 03:00 / завтра в 03:00 /
  своё время…) применяется к любой кнопке запуска — задание ставится с
  `scheduled_at`, и runner не берёт его до срока (точность ≈ 2 с; пояс пресетов —
  env `TZ` контейнера web, по умолчанию Europe/Moscow). «Своё время…» — точные
  дата и время: календарь (`st.date_input`, ДД.ММ.ГГГГ) ограничен сегодняшним
  днём, а «сегодня, но время уже прошло» даёт предупреждение и блокирует кнопки
  (молчаливого переноса на завтра нет — выбор даты явный). Очередь показывает
  каждое задание с обратным отсчётом и действиями «▶️ Сейчас» (снять отсрочку),
  «⏰ +1 ч», «✖ Отменить» (не начатое задание → stopped «не начато», слот той же
  команды освобождается); одно отложенное задание не блокирует немедленный
  запуск других команд.
* **Журнал** (фрагмент): хвост `events` (последние 200) с автообновлением и
  кнопкой **«🧹 Очистить журнал»** (с подтверждением, если `ui.confirm_clean_log`).
* **Галерея**: пагинация по `page_size` групп; кнопка **«🔄 Обновить»**.
  Автообновление после прогона (1.7.0): фрагмент Монитора (он опрашивает БД
  каждые `ui.refresh_sec` независимо от активной вкладки) видит переход
  «движок/задание заняты → освободились» и делает ОДИН полный rerun приложения —
  галерея перечитывает данные, кнопки разблокируются; постоянный поллинг
  галереи не включён намеренно — перерисовка сотен миниатюр тяжела для
  браузера при 3 ТБ архивах (ручная кнопка остаётся для CLI-прогонов и
  ручных операций); для группы — пути, размеры, подтверждение (manual); тумблер
  «🖼 Показать изображения»; **под каждой картинкой — ряд кнопок-иконок**:
  ⭐ «Это оригинал» (вернуть в исходное место, прежний оригинал → в trash),
  📋 «Это дубликат» (перенести в trash), ↩️ «Вернуть» (работает для перенесённых),
  🗑️ «Удалить» (с диска; подтверждение — если `ui.confirm_delete_files`),
  ℹ️ «Свойства» — модальное окно с EXIF (тип, размеры, камера, выдержка,
  диафрагма, ISO, вспышка, замер, фокусное, дата съёмки) и дублирующим
  набором кнопок. Раскрытая группа остаётся раскрытой после операций
  (состояние в `session_state`).
* **Логика** (вкладка): рендерит `docs/LOGIC.md` из примонтированного каталога
  `./docs:/app/docs:ro` — документация видна из UI без пересборки образа.
* В web-контейнере `src` и `trash` смонтированы **rw** — на них работают
  точечные операции ⭐/📋/↩️/🗑️/undo (без обходов ФС, только по путям из БД);
  во время работы движка все мутирующие кнопки отключены (guard по `status`).
* **Почему кнопки запуска сделаны через очередь, а не docker-сокет** (1.5.0):
  docker-сокет в web-контейнере — это root-доступ к хосту, а владение
  долгоживущим процессом противоречит модели Streamlit и принципу тонкого
  клиента. Кнопки запуска лишь вставляют строки в `jobs` —
  выполняет отдельный сервис `runner` (тот же образ/код, что и CLI).
  Подробное обоснование и схема — `docs/WHY_NO_BUTTONS.md` (§5 — реализованный
  вариант A). Всё, что UI может делать без владения процессом
  (Стоп, undo, очистка БД, копирование команды запуска), уже реализовано.

## 7. Маунты, тома, права

Где лежат фото на хосте — задаёт `PHOTOS_ROOT` в `.env` (образец `.env.example`;
по умолчанию `./`):

| Маунт | engine | web | Зачем |
|---|---|---|---|
| `${PHOTOS_ROOT}/src → /data/src` | rw | rw | Архив: движку — перенос из него, UI — точечные операции ⭐/↩️ |
| `${PHOTOS_ROOT}/trash → /data/trash` | rw | rw | Приёмник дубликатов: движку — перенос, UI — 📋/🗑️/undo |
| `./settings.toml` | `/app/settings.toml` **ro** | `/data/settings.toml` **rw** | Единый файл настроек (решение описано в §3) |
| `./docs → /app/docs` | — | **ro** | Вкладка «🧠 Логика» (LOGIC.md) без пересборки образа |
| volume `pgdata` | — | — | Данные PostgreSQL |
| volume `thumbs` (`/data/cache`) | — | rw | Дисковый кэш миниатюр |

Контейнер работает под non-root пользователем `appuser` (uid 1000). Bind-маунты
`./src` и `./trash` сохраняют права host-системы: создайте их своим пользователем
(`mkdir -p src trash`), тогда запись будет разрешена. Если ваш uid ≠ 1000 —
`sudo chown -R 1000:1000 trash` (или поправьте `useradd --uid` в Dockerfile).

`.dockerignore` исключает `src/`, `trash/`, `settings.toml` из образа.

## 8. Измерение производительности UI (цель < 300 мс)

**Что измеряется**: полный реран скрипта Streamlit — wall-time от начала до конца
рендера, `time.perf_counter()`; в приложении это метрика **«UI rerun, мс»** в сайдбаре
(плюс avg(10) и max(30) по сессии). Автообновляемые вкладки работают как
`st.fragment` и реранятся **отдельно от страницы**, их локная длительность выводится
каптионом внутри фрагментов («фрагмент обновлён за N мс»).

**Как воспроизвести**:

1. `docker compose up -d db web`, открыть http://localhost:9501.
2. В соседнем терминале запустить движок на большом наборе:
   `docker compose run --rm engine run` (индексация на полной скорости).
3. Не закрывая терминал движка, в UI: подержать открытой вкладку «Монитор»
   (фрагменты тикают каждые `refresh_sec`), полистать страницы «Галереи»,
   попереключать вкладки — и снимать значения «UI rerun, мс».

**Зафиксированный критерий**: устойчиво **< 300 мс** при работающем движке.
Достигается: все запросы — LIMIT/агрегаты через пул (max 5), галерея — постранично,
миниатюры ленивые из дискового кэша, тяжёлые вкладки — фрагменты (перерисовывается
только вкладка). Если метрика превышает 300 мс — смотрите «Журнал» (нагрузка БД),
увеличьте `refresh_sec`, проверьте, что запросы не были заменены на неограниченные.

## 9. Приёмка (критерии и как проверить)

1. **Quickstart работает** — команды из §2 поднимают db+web+runner и запускают движок.
2. **Повороты/отражения находятся** — `scripts/make_testset.py` создаёт оригиналы
   и копии (90/180/270, отражения, диагонали, resize+перекодирование); после
   `engine run` в галерее каждая копия попадает в группу к оригиналу (для пущей
   строгости: `engine run --dry-run` покажет план без переноса).
3. **kill -9 не портит БД, run продолжает** — во время scan:
   `docker ps --filter ancestor=photo-dedup:1.7.1 -q | xargs -r docker kill` (или
   `pkill -9 -f engine.cli` при локальном запуске), затем снова
   `docker compose run --rm engine run` — сканирование продолжится с места
   остановки (закоммиченные батчи пропускаются по `(path,size,mtime)`).
4. **UI отзывчив при индексации** — метрика «UI rerun, мс» < 300 при работающем
   движке (§8).
5. **auto-перенос создаёт папки групп с info.txt** — после `engine run` (mode=auto)
   в `./trash` появляются папки, названные по оригиналу (`_IMG_…jpg`, при
   коллизиях `__2`), с `info.txt`; галерея показывает `moved_to`-пути (файлы
   читаются из trash), `group_members.moved_to` заполнено.
6. **Ручные операции и отмена** (1.4.0): в галерее ⭐ на перенесённом дубликате
   возвращает его в src, а текущий оригинал физически уезжает в trash
   (роли и `kept_path` меняются); ↩️ возвращает без смены роли; 🗑️ удаляет
   с диска (после подтверждения); `engine undo --dry-run` показывает план,
   `engine undo` возвращает все файлы в src и очищает БД — trash остаётся
   без изображений, `engine status` показывает пустой индекс.
   С 1.4.3: ⭐/📋 работают и когда папки группы в trash ещё нет — она
   создаётся автоматически (ручной режим до первого `engine move`).
7. **Свойства и журнал** (1.4.0): ℹ️ на картинке показывает EXIF
   (камера/выдержка/ISO/дата съёмки) — они заполнены при `scan.read_exif=true`
   (проверка: `SELECT exif FROM files WHERE exif IS NOT NULL LIMIT 1`);
   «🧹 Очистить журнал» опустошает events, «💥 Очистить БД» — результаты и журнал.
8. **Запуск из UI через очередь** (1.5.0 Ф1 + 1.6.0 Ф2): на Мониторе кнопки
   «▶️ Полный прогон», «🔍 Скан», «🧠 Анализ», «📦 Перенос», «↩️ Undo» (с
   подтверждением) ставят задания в `jobs` (`SELECT id,command,state,exit_code
   FROM jobs ORDER BY id DESC LIMIT 5`); сервис `runner` забирает их за секунды
   (лог: `docker compose logs runner`), статус проходит
   `queued → running → done`; пока задание живо, кнопки заблокированы
   (двойной клик отсекает и уникальный индекс `uniq_jobs_queued_command`);
   «🛑 Стоп» во время runner-прогона завершает задание со state=`stopped`;
   обрыв runner'а (kill -9 контейнера) находит UI: stale-задание получит
   предупреждение «⚠️ Прогон оборвался» (reap по heartbeat из UI и на старте
   runner'а); история очереди не растёт бесконечно — retention
   (`RUNNER_RETAIN_JOBS=200`), а «💥 Очистить БД» вычищает её целиком.
9. **Отложенный запуск** (1.7.0 Ф3; выбор даты — 1.8.0): выберите «сегодня в 03:00» в селекте
   «Когда запускать» и нажмите «🔍 Скан» — задание появится в `jobs` со
   `scheduled_at` (`SELECT id,command,scheduled_at,state FROM jobs WHERE
   state='queued'`), runner не возьмёт его до срока (лог: runner молчит),
   а в очередь можно поставить другие команды немедленно. Действия над
   очередью: «▶️ Сейчас» снимает отсрочку (задание берётся за секунды),
   «✖ Отменить» переводит задание в stopped «не начато» и освобождает слот
   uniq-индекса. Выбор точной даты: «Своё время…» — будущая дата/время кнопки
   активны, дата на две недели вперёд ставится так же; прошедшее время сегодня
   — предупреждение «⏰ … уже в прошлом» и заблокированные кнопки. После
   завершения прогона галерея обновляется сама (без F5), а кнопки разблокируются.
10. **Блоки опасных зон не дублируются, manual-блок по режиму** (1.7.1):
   после завершения Прогона/Скан на Мониторе ровно по одному expander'у
   «⚠️ Опасная зона: подтверждение переноса (manual)» (только при
   `move.mode=manual`) и «🧨 Опасная зона: обслуживание БД» — без вторых копий
   до перезагрузки страницы; переключение mode в сайдбаре туда-обратно
   (`manual → Сохранить → auto → Сохранить`) скрывает manual-блок в auto.

## 10. Известные ограничения

* Бакетный префикс 16 бит (по умолчанию): пары, различающиеся в первых 16 битах
  хэша, не сопоставляются (осознанный trade-off скорости, §4). Байт-в-байт
  копии при этом НЕ теряются никогда: у идентичных файлов совпадает весь phash,
  поэтому они всегда попадают в один бакет и находятся при любом threshold
  (дополнительно верифицируются sha256 на этапе move).
* phash — перцептивный хэш: близкие по смыслу кадры (серии съёмки) могут попадать
  в группы; регулируется `threshold` (0–4 консервативно, выше — агрессивнее).
  Точные копии внутри группы (равенство sha256 с оригиналом) помечаются
  автоматически — см. §4, этап move.
* Векторизованное сравнение в analyze требует хэшей ≤ 64 бит (hash_size ≤ 8);
  при больших — автоматический резерв на чистом Python (медленнее).
* HEIC/HEIF — опционально: раскомментируйте `pillow-heif` в `requirements.txt`
  и пересоберите образ.
* `refresh_sec` применяется после перезапуска web-контейнера (фрагменты создаются
  на старте процесса); остальные настройки UI — сразу, движка — на границе этапов.

## 12. Изменения в 1.9.0 (CLI: отложенный запуск из командной строки — schedule --at/--delay)

Ф3-хвост №2: отложенный запуск был доступен только из UI (кнопки Монитора),
хотя очередь jobs с самого начала задумана как клиентская и для CLI
(docs/WHY_NO_BUTTONS.md §5). Из терминала «запуск в пятницу утром» выражался
только сном/cron-обёртками вокруг `docker compose run`.

* Новая подкоманда **`engine schedule JOB (--at MOMENT | --delay DELAY)`**,
  JOB ∈ {run, scan, analyze, move, undo} — те же команды, что ставит в очередь
  UI. Постановка — INSERT + pg_notify в jobs, выполняет сервис runner:
  runner и БД не менялись (тот же фильтр срока в `claim_next`, single-flight,
  uniq-индекс — одно queued-задание на команду).
* Форматы: `--at` — «ГГГГ-ММ-ДД ЧЧ:ММ[:СС]», «ДД.ММ.ГГГГ ЧЧ:ММ[:СС]»,
  «ЧЧ:ММ» (сегодня) и дата без времени (= 00:00); `--delay` — «90» (минуты)
  или сегменты «45m», «2h», «1d», «1d12h». Ровно один из флагов (иначе rc 2).
* Пояс: момент считается в `TZ` (как у пресетов UI); в engine-сервис compose
  добавлен `TZ` — раньше он был только у web/runner. В БД уходит абсолютное
  мгновение (TIMESTAMPTZ) — смена пояса не сдвигает запланированное.
* Валидация: прошедший момент — ошибка (rc 2) БЕЗ молчаливого переноса на
  завтра (семантика «Своё время…», 1.8.0); настройки и пути проверяются ДО
  постановки в очередь — отложенное задание не «выстрелит» спустя часы с rc 2
  из-за опечатки; дубликат queued-команды — понятное сообщение и rc 1
  (uniq-индекс БД), а не traceback.
* Параметры прогона (`--threads`, `--threshold`, `--dry-run`, `--move-mode`,
  `--keep-by`, `--force`, `--group-id`) уходят в `jobs.params` и применяются
  runner'ом в момент выполнения (та же схема, что читает `execute_job`).
* `schedule` не создаёт trash и не трогает файлы — только INSERT в очередь;
  перенос/отмена поставленного — блок «Очередь runner» в UI.

**Тесты**: smoke §15 (парсеры `_parse_at`/`_parse_delay` с инъекцией now:
ISO/ДД.ММ.ГГГГ/ЧЧ:ММ/дата, сегменты delay, мусор и ноль, взаимное исключение
флагов; пины: choices=jobs.COMMANDS, UniqueViolation→rc 1, TZ у engine-сервиса);
integ §18k (живой PostgreSQL: `schedule run --delay 90m --threads 3` → queued
с params и scheduled_at ≈ +90 мин; дубликат rc 1; прошедший/оба флага/битый
--at rc 2; вторая команда ставится свободно); smoke/integ/kill9 — зелёные.

## 14. Изменения в 1.7.1 (хотфикс: задвоение «Опасных зон» после прогона; manual-блок в auto)

Два дефекта UI, найденных в эксплуатации 1.7.0.

**Задвоение блоков «Опасная зона» после Прогона/Скан.** После завершения задания
на Мониторе оба блока опасной зоны (и иногда соседние элементы) отображались
дважды до перезагрузки страницы. Причина: автообновление галереи (1.7.0)
выполняло полный `st.rerun(scope="app")` в СЕРЕДИНЕ фрагмент-рана — после того,
как фрагмент уже отрисовал метрики/кнопки. Прерывание фрагмент-рана с уже
сгенерированными дельтами — известное слабое место клиентского рендера
Streamlit (см. их issue про фрагменты, пишущие «не в свой слот»): хвост
фрагмента оставался в DOM второй копией. Фикс: блок снятия метрик очереди и
cам edge-детект перенесены в САМОЕ НАЧАЛО `monitor_fragment` — полный rerun
происходит до генерации каких-либо дельт фрагмента (прерывать нечего).
Автообновление галереи работает как прежде (проверено: группы свежего прогона
появляются в галерее без F5).

**Блок «⚠️ Опасная зона: подтверждение переноса (manual)» скрывается в auto.**
Блок рендерился независимо от `move.mode`. В auto move переносит ВСЕ группы
последнего run, `confirmed` не учитывается (`engine/move.py`) — подтверждения
ни на что не влияли. Теперь блок показывается только при `move.mode=manual`
(в auto остаётся только «🧨 Обслуживание БД», вынесенное в общий помощник
`_db_ops_block`).

**Тесты**: smoke §14 (пины: mode-условие над expander'ом, `_db_ops_block`,
edge-детект до `c1.metric`, ровно один `st.rerun(scope="app")`);
smoke/integ/kill9 — зелёные.

## 15. Изменения в 1.7.0 (Ф3: отложенный запуск; автообновление галереи после прогона)

Две фичи из запросов эксплуатации: запуск прогона «на ночь» без терминала и
автоматическая актуализация галереи без перезагрузки страницы.

**Отложенный запуск (`jobs.scheduled_at`, Ф3)**

* Миграция: `ALTER TABLE jobs ADD COLUMN IF NOT EXISTS scheduled_at TIMESTAMPTZ`
  (идемпотентная, выполняется при старте движка/runner'а; NULL = «как можно
  скорее» — прежнее поведение всех кнопок).
* `engine/jobs.py`: `enqueue(..., scheduled_at=None)`; `claim_next` не берёт
  задания из будущего (`AND (scheduled_at IS NULL OR scheduled_at <= now())`);
  новые операции UI — `reschedule` (перенос отсрочки, None = снять) и
  `cancel_queued` (не начатое задание → stopped «не начато», слот
  `uniq_jobs_queued_command` освобождается); `snapshot` отдаёт `queued_jobs`
  с деталями отсрочки. Runner не менялся: до срока `claim_next` возвращает
  None, старт в срок с точностью ≈ `RUNNER_POLL_SEC` (2 с).
* UI: селект **«Когда запускать»** (Сейчас / через 30 мин / 1 ч / 3 ч /
  сегодня в 03:00 / завтра в 03:00 / своё время) над кнопками запуска —
  применяется к любой из них; пресеты считаются в поясе `TZ` контейнера web
  (по умолчанию Europe/Moscow; в БД хранится абсолютный момент, смена пояса
  не сдвигает запланированное). Очередь показывает каждое задание с обратным
  отсчётом и действиями **«▶️ Сейчас»** (снять отсрочку), **«⏰ +1 ч»**,
  **«✖ Отменить»**. Одно отложенное задание НЕ блокирует немедленный запуск
  других команд (блокируют только running и «созревшие» queued); дубль той же
  команды по-прежнему отсекает uniq-индекс.
* Семантика: «не раньше», а не «ровно в» — если к сроку движок занят
  (single-flight), задание выполнится, когда освободится; при простое стека в
  момент срока задание выполняется при старте (догоняющее). Это разовый сдвиг,
  а не cron: повторяющиеся прогоны — хостовым cron
  (`docker compose run --rm engine scan`).

**Автообновление галереи после прогона**

* Фрагмент Монитора и так опрашивает БД каждые `ui.refresh_sec` независимо от
  активной вкладки; добавлена edge-детекция перехода «движок/задание заняты →
  освободились»: на границе выполняется ОДИН полный `st.rerun(scope="app")` —
  галерея перечитывает данные, кнопки разблокируются (без F5). Постоянный
  поллинг галереи не включён намеренно (перерисовка миниатюр тяжела при
  больших архивах); кнопка «🔄 Обновить» остаётся для CLI-прогонов и ручных
  операций.

**Тесты**: smoke §13 (пины Ф3: DDL-миграция, фильтр срока в claim_next,
reschedule/cancel_queued, селект и edge-детекция, TZ в compose/.env.example);
integ §18j (живой PostgreSQL: задание из будущего не берётся, reschedule →
немедленный взбор, cancel_queued → stopped «не начато» + освобождение слота
uniq-индекса, прошедший срок берётся сразу, running reschedule/cancel не
трогают); smoke/integ/kill9 — зелёные.

**Документация**: README (§6, §9, §11, этот раздел), ARCHITECTURE (§2/§4),
UI_DESIGN (§6), WHY_NO_BUTTONS (шапка, §6), .env.example (TZ).

## 16. Изменения в 1.6.1 (хотфикс: кнопки очереди падали с KeyError: 0)

**Симптом.** При нажатии ЛЮБОЙ кнопки запуска на Мониторе (▶️/🔍/🧠/📦/↩️) —
ошибка `KeyError: 0` в `jobs.enqueue` (строка `cur.fetchone()[0]`), задание в
`jobs` не попадало. Причина: пул соединений web создан с
`kwargs={"row_factory": dict_row}` (запросы UI читают строки по именам
колонок), а `engine/jobs.py::enqueue` извлекал `RETURNING id` по индексу
`[0]` — на dict-строке это `KeyError`. INSERT при этом успевал выполниться и
откатывался пулом при исключении — потому «в таблицу не добавляется».
Integ-тест пропустил дефект: §18 проверял enqueue через соединение движка с
кортежными строками (дефект существовал с 1.5.0; кнопка Ф1 не проверялась
вживую до Ф2).

**Фикс.**

* `engine/db.py::first_value(row)` — извлечение первого столбца строки,
  независимое от row_factory (кортеж ИЛИ dict); `db.scalar` переведён на него.
* `engine/jobs.py::enqueue` — `int(db.first_value(cur.fetchone()))`.
* `engine/webops.py::clean_db` — те же два счётчика через `first_value`
  (латентный дефект того же класса: «💥 Очистить БД» упало бы так же).

## 17. Изменения в 1.6.0 (Ф2: все длинные команды в очереди, stale-детекция, retention)

**Контекст.** Ф1 (1.5.0) дал очередь и runner с одной кнопкой полного цикла.
Ф2 доводит схему до полного плана: в очереди — ВСЕ длинные команды, обрывы
runner'а видны в UI, история очереди не растёт бесконечно. Архитектура не
менялась: те же таблица `jobs`, сервис `runner` (без docker-сокета) и тонкий
клиент; `clean-db`/`status`/`stop` и точечные webops-операции остались прямыми.

**Новое.**

* **Кнопки всех длинных команд на Мониторе**: «▶️ Полный прогон» (`run`),
  «🔍 Скан», «🧠 Анализ», «📦 Перенос», «↩️ Undo» — каждая ставит задание в
  `jobs` (INSERT + `pg_notify`), выполняет сервис `runner`. Undo — только
  через двухфазное подтверждение («✅ Да, вернуть файлы»); пока есть живое
  задание или работает движок, все кнопки заблокированы (single-flight).
  Помощь каждой кнопки описывает охват этапа; `move.dry_run`/`move.mode`
  по-прежнему читаются из settings.toml (сайдбар главнее).
* **Stale-детекция в UI**: Монитор при каждом обновлении выполняет
  `reap_stale` по тому же порогу `RUNNER_STALE_SEC` (30 с по умолчанию; env
  читают и runner, и web) — обрыв runner'а виден, даже если контейнер ещё не
  перезапустился. Состояние stale показывает предупреждение
  «⚠️ Прогон оборвался» с подсказкой Resume (запустить этап заново — scan/move
  продолжат с места остановки).
* **Retention истории очереди**: `engine/jobs.py::prune` хранит последние

  его после каждого `finish`. «💥 Очистить БД» теперь вычищает и очередь
  (`TRUNCATE_ALL` включает `jobs`), отчёт в журнале это упоминает.
* **Тексты UI** синхронизированы: баннер, «что дальше» (manual-шаг 2 — кнопка
  «📦 Перенос»), «⌨️ Быстрые команды», подсказка опасной зоны (когда выбирать
  очередь вместо прямого undo), docstring.
* **compose/.env.example**: `RUNNER_RETAIN_JOBS` (runner), `RUNNER_STALE_SEC`
  передаётся и в web (общий порог stale).

## 18. Изменения в 1.5.0 (job-runner Ф1: кнопка «▶️ Запустить прогон» через очередь jobs)

**Контекст.** Запуск движка был только из терминала (docs/WHY_NO_BUTTONS.md):
кнопка через docker-сокет отвергнута по безопасности и архитектуре. Согласована
схема «вариант A»: **in-process runner** (тот же образ/код, что и CLI) +
**очередь заданий в PostgreSQL** (Redis отклонён: задание — durable-данные,
как events; SKIP LOCKED + LISTEN/NOTIFY покрывают всё, минус компонент).
Этап Ф1 = таблица `jobs` + сервис `runner` + кнопка запуска полного цикла.

**Новое.**

* **Очередь `jobs` в PostgreSQL** (`engine/db.py`, идемпотентная миграция):
  `command (run/scan/analyze/move/undo)`, `params JSONB`, `state`
  (`queued → running → done/failed/stopped/stale`), `requested_at`/`taken_at`/
  `finished_at`/`heartbeat_at`, `runner_id`, `exit_code`, `error`, `result JSONB`.
  Частичный уникальный индекс `uniq_jobs_queued_command` — одно queued-задание
  на команду (двойной клик/гонка вкладок отсекаются на уровне БД). `clean-db`,
  `stop`, `status` в очередь не входят — остаются прямыми операциями.
* **`engine/jobs.py`** — операции очереди: `enqueue` (INSERT + `pg_notify`),
  `claim_next` (атомарный взбор `SELECT … FOR UPDATE SKIP LOCKED` +
  single-flight guard «движок уже работает?»), `heartbeat`, `finish`,
  `reap_stale` (crash-recovery: зависшие running → stale на старте runner'а;
  штатный Resume команд продолжит работу), `snapshot` (данные Монитора).
* **`engine/runner.py`** — сервис job-runner (`python -m engine.runner`):
  вечный цикл — LISTEN/NOTIFY (мгновенное пробуждение; фоллбэк — опрос раз в
  `RUNNER_POLL_SEC`=2 с), взбор задания и **in-process** выполнение команды
  движка тем же кодом, что и CLI, — без subprocess и повторного argparse
  (параметры задания маппятся в те же overrides, что и CLI-флаги).
  Heartbeat отдельным потоком (раз в `RUNNER_HEARTBEAT_SEC`=5 с); SIGTERM —
  мягкая остановка задания (второй сигнал — принудительный выход, контейнер
  перезапустится, задание станет stale); итог — state/exit_code/error/result
  (state=`stopped` при мягкой остановке через «🛑 Стоп» — флаг тот же).
* **docker-compose: сервис `runner`** — тот же образ, маунты src/trash/settings
  (`settings` — ro), env engine + `RUNNER_*`, `restart: unless-stopped`,
  БЕЗ docker-сокета. CLI `docker compose run --rm engine …` не изменён.
* **UI (Монитор)**: кнопка **«▶️ Запустить прогон»** — INSERT в `jobs`
  (дубль отсекается индексом — toast «уже в очереди»); блок очереди:
  «⏳ в очереди» / «🏃 runner выполняет #id (взял HH:MM:SS)» и история
  последних 5 заданий (state, exit code, длительность, первые 90 символов
  ошибки). Кнопка заблокирована при queued/running задании или работающем
  движке. Тексты баннера, информера «что дальше» и «⌨️ Быстрые команды»
  обновлены. Тонкий клиент не ослаблен: UI по-прежнему не запускает процессы.
* **Схема БД**: только добавление (jobs + индексы), идемпотентно; старые БД
  поднимаются автоматически при первом старте движка/runner'а.

**Тесты**: smoke §5 (8 таблиц) и §10 (пины Ф1: compose/DDL/jobs/runner/UI);
integ §18 на живом PostgreSQL: enqueue/дубль-индекс, claim SKIP LOCKED,

## 19. Изменения в 1.4.3 (фиксы галереи: ⭐/📋, модальное окно)

Три багрепорта из ручного режима — все исправлены в UI-слое и webops:

1. **⭐/📋 больше не падают, когда папки группы в trash ещё нет.** В ручном
   режиме это штатная ситуация (до `engine move` папок в trash не существует):
   `_demote_to_trash` (`engine/webops.py`) переносил файл в несуществующую
   папку → «[Errno 2] No such file or directory: …/trash/_IMG_….jpg/2.jpg».
   Теперь папка создаётся перед переносом (`mkdir(parents=True, exist_ok=True)`,
   как на этапе move). Попутно имя новой папки приведено к конвенции move.py:
   она называется по ОРИГИНАЛУ группы (при 📋 у текущего оригинала — по
   автоматически выбранному новому), а не по переносимому файлу — иначе группа
   дробилась бы между двумя папками в trash.
   ВАЖНО: сами кнопки ⭐/📋 в ручном режиме — НЕ ошибка дизайна: это и есть
   ручной workflow (информер: «Отметьте файлы кнопками ⭐/📋 в Галерее»);
   дефект был только в создании папки.
2. **В модальном окне «ℹ️ Свойства» больше нет кнопки ℹ️** — она открывала
   то же окно изнутри его самого. Ряд кнопок в окне: ⭐ 📋 ↩️ 🗑️.
3. **Подтверждение удаления не закрывает модальное окно.** Раньше 🗑️ в окне
   делал полный `st.rerun` → окно закрывалось, а ❗/❌ появлялись под картинкой
   в сетке. Диалог в Streamlit работает как фрагмент (перерисовка по клику
   без полного rerun), поэтому подтверждение теперь живёт внутри окна:
   🗑️ → ❗/❌ в окне; полный rerun — только после самого удаления (окно
   закрывается, галерея обновляется). Состояние подтверждения в окне отдельное
   (`dlgarm_*`), сбрасывается при новом открытии окна; отменить ❌ можно
   тоже внутри окна.

* Тесты: smoke §8 (функционально, без БД: mkdir несуществующей папки группы +
  коллизии имён — воспроизведение кейса багрепорта), §9 (source-пины всех
  фиксов); инварианты webops согласованы с move.py.
* Изменены: `engine/webops.py`, `web/app.py`; версии в compose; доки.

  (это и есть натуральная единица этапа), на scan/move — «файлов/с» (CLI `status`
  и монитор UI). ETA считается в тех же единицах, т.е. остаётся корректным.
* **БД: строки перенесённых/исчезнувших файлов помечаются `status='moved'`**
  (раньше они оставались «мёртвыми» строками со статусом `'ok'`). История групп
  и галерея сохраняются; счётчики в `engine status` показывают
  «перенесено/отсутствует» отдельно; вернувшийся на то же место файл
  переиндексируется обратно в `'ok'`.
  Миграция CHECK-ограничения идемпотентна и выполняется при каждом старте движка
  (старые БД поднимаются автоматически).
* **move: детерминированный crash-recovery при одноимённых дубликатах.** Раньше
  два дубликата с одинаковым именем в одной группе могли «приклеиться» к одному
  и тому же файлу в trash (второй оставался неучтённым). Теперь recovery
  повторяет аллокацию имён `_unique_target` (base, base_1, base_2…) в порядке
  членов группы и не переиспользует занятые слоты; хэши восстановленных
  файлов тоже удаляются, `moved_at` доносится.
* **scan: подсчёт файлов-кандидатов в фоновом потоке** — устранён отдельный
  блокирующий обход дерева до хэширования (двойной обход); знаменатель
  прогресс-бара подтягивается, как только счёт готов.
* Тесты: smoke 1h (атомарная запись), integ §10 (батч-запрос членов страницы),
  §13 (recovery одноимённых дубликатов, `files.status='moved'`, moved_at/хэши).

## 24. Изменения в 1.2.0

* **move: новая политика оригинала `keep_by=capture` (новый дефолт).** Оригинал
  определяется по времени снимка: json-Takeout-sidecar (`photoTakenTime` →
  `creationTime`) → файловая система (`min(birthtime, mtime)`, на Windows —
  `st_ctime`) → тай-брейк по «копийным» маркерам имени (`(Copy 2)`, `(1)`,
  ` — копия`, `-edited` проигрывают чистому имени) → путь. Решает кейс, когда
  `IMG_20260912_163920.jpg` шёл после своих `(Copy N)` по сортировке и
  считался дубликатом. Старые политики `size`/`pixels` доступны как и раньше
  (CLI `--keep-by`, settings.toml, UI).
* **move: папки групп называются по оригиналу** (`_IMG_20260914_123649.jpg`
  вместо `group_N`, префикс настраивается `move.group_name_prefix`).
  Санитизация под Windows/macOS/Linux, уникальность без учёта регистра (NFC),
  коллизии между группами — `__2`, `__3`. Имя папки пишется в `groups.info`
  (`group_dir`); в `info.txt` добавлены время снимка оригинала и его источник.
* **analyze/move**: в подсказку kept на analyze добавлен mtime из БД;
  crash-recovery ищет перенесённые файлы и в именованных папках групп,
  и в прежних `group_{id}` (с проверкой размера).
* Тесты: smoke §6 (парсер Takeout-времён, name-penalty, capture-выбор,
  санитизация/коллизии имён), integ §12 (json-sidecar vs ФС, чистое имя против
  `(Copy N)`, коллизии папок групп), обновлены интеграционные проверки нейминга.

## 25. Изменения в 1.1.0

* **analyze: устойчивость и память.** Попарное сравнение в бакете переведено на
  2D-блоки — пик памяти ограничен десятками МБ независимо от размера бакета
  (раньше блок 2048×n на «плоском» бакете из 30 тыс. похожих кадров расходовал
  ~1,3 ГБ). Хэши разной длины (смена `hash_size` без `--force`) больше не роняют
  analyze с `OverflowError`: бакет делится на подгруппы равной длины.
* **move: dry-run полностью read-only.** Раньше при отсутствующих файлах группы
  dry-run изменял БД (удалял хэши, писал `groups.info`) — теперь в dry-run не
  выполняется ни одной записи: действия только планируются в events.
* **move: точная верификация копий по sha256.** Дубликаты каждой группы
  хэшируются sha256; равные оригиналу помечаются в dry-run-плане, в `info.txt`
  и в `groups.info` (`exact_kept_copies`, `dups_sha_checked`). Байт-в-байт копии
  гарантированно находятся при любом threshold (совпадение полного phash).
* Тесты: smoke 2e/3e/3f (sha256, 2D-чанкинг, смешанные длины), integ 11a/11b
  (dry-run read-only, sha256-верификация).
